# 0.8.5 起点：遮罩首帧交接（未完成，勿直接合入）

0.8.4 为控制风险只保留「打开任务不再同步重绘」这一处（G1a 崩溃入口）。下面这套
「等遮罩首帧再 apply」的实现在 `wip/0.8.5-overlay-handoff` 上冻结，作为 0.8.5 的
起点：它解决了 CX-31 §2 的可见性回归，但 CX-32 又找出两项阻断，改动面已经超出
0.8.4 该冒的险。

## 已实现（分支上的代码）

- `folith/qt/components.py`：`LoadingOverlay.run_after_next_paint(callback)`，由遮罩
  自身 `paintEvent`（`painter.end()` 之后）触发一次；回调只允许排队。
- `folith/qt/loading_handoff.py`：`PaintingHandoff` 用窗口 `_later` 排续段、单 pending
  槽 + serial、`FRAME_FALLBACK_MS = 250` 无帧兜底；`apply_workbench_refresh(...)` 是
  `_refresh_workbench` 的共用尾部。
- `folith/qt/window.py`：`_refresh_workbench` 延迟时返回 `True`，`refresh_workbench`
  的 `finally` 此时不隐藏也不 flush，续段应用完再收尾。
- 测试：真实窗口 `paint → apply → dismiss` 顺序、等待首帧时的二次刷新只应用一次；
  `qt_workbench_poll_test.py` 的 `_pump_settled`。

## CX-32 的两项阻断（0.8.5 必须先解决）

1. **轮询能绕过待首帧的交接。** 待首帧没有进入 `_state_load_in_flight` /
   `_pending_poll` 的串行化条件。全量轮询的同签名快路径会直接 `workbench.apply`
   并在 `finally` 隐藏遮罩，然后 250 ms 兜底再跑一次原续段——同一任务被应用两次，
   遮罩被提前隐藏。`folith/qt/window.py` 的 `_poll_workbench_full` 在
   `refresh_workbench(preloaded=True)` 时也没把 `_cached_models` 传下去，于是
   `models=None` 的请求可以替换掉待应用的后台投影；慢投影完成回调更新
   `_cached_state` 后，旧续段还会把旧 `models` 混进新状态。
2. **续段守卫缺导航代次与计时连续性。** `PaintingHandoff.cancel()` 没有调用方；
   同一任务离开再打开时任务 ID 会重新相等，旧续段不认识新的导航代次。第一次刷新
   的 `_PhaseLog` 只记到等待开始，续段另起一份记录，读盘/准备页/等待时间丢失。

方向（CX-32 §2）：让待首帧的刷新参与现有轮询串行化，已排队的读取回调与新轮询
合并或标记重发；续段核对任务、导航代次，按成对的 `state/models` 应用；接管新导航
时显式撤销旧请求；计时与隐藏随被认可的请求收尾。

参考：`.audit/2026-11-28-cx31/report.md` §2、`.audit/2026-11-28-cx32/report.md` §2。
