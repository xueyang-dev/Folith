# P2-11：保存失败后的「以磁盘为准」刷新不在 GUI 线程整份读状态

日期：2026-11-15。分支 `fix/0.8.2-p2-11-async-failure-refresh`，基于 main `243a2a66`（不 rebase）。
只改 `folith/qt/window.py` 的失败路径，加一条测试。

## 1 证据（P2-0r2 从第二轮数据读出来的第一名）

S1 R（两臂各 3 轮 × 600 s，1000 段、TS=1.0、真实窗口）三轮合计：

| | 候选 | 基线 |
| --- | --- | --- |
| `window.py failed → refresh_workbench → _refresh_workbench → …` 族 | **62 次 / 7.46 s / 36.9%** | **65 次 / 8.30 s / 52.0%** |
| 其中整份读回那条（`adapter.load_state → core.load_job_state`） | 9 次 / 1.13 s | 11 次 / 1.37 s |
| 走 `views.apply → _render_segment…` 的那条 | 12 次 / 1.42 s | 9 次 / 1.10 s |
| 走 `views.apply → _render_delivery` 的那条 | 7 次 / 0.86 s | 9 次 / 1.20 s |

两臂的**产品侧第一名都是它**（候选 36.9%、基线 52.0%），而且候选里还在
（`window.py:2971`，基线 `window.py:2470`，行号不同是因为两臂代码不同）。

机制：`_save_next_edit()` 的 `failed` 回调为了让界面「显示磁盘上真实的样子」调
`refresh_workbench(force=True)`；`_refresh_workbench` 在 `force=True` 且不是 preloaded 时
**同步** `adapter.load_state(job_id)`——解析 + 安全深拷贝。10,000 段任务上单次 0.2–1.1 s
（P2-13 的微基准：30.4 MB 状态 169–436 ms；GUI 线程上采样到 1,071–3,358 ms）。
失败路径恰好是重试循环反复落到的地方。

## 2 改法

`folith/qt/window.py`

- 新增 `refresh_workbench_soon()`：只要求「磁盘为准」，不等结果。它丢掉增量游标
  （`_drop_delta_state`，否则下一次 delta 会落在已经被替换的行上）、置
  `_force_full_poll`、叫 `_poll_workbench()`。
- `_poll_workbench()` 认这个标记，直接走整状态路径（不让 delta feed 短路掉它）。
- `_poll_workbench_full(force=False)`：把 `force` 传到最后的
  `refresh_workbench(force=force, preloaded=True, models=models)`，所以 apply 的宽度
  和原来的同步 `force=True` 完全一样（准备页重算、交付重新校验、段落行重画）。
- 整状态路径里「签名没变」的那个短路分支改为
  `refresh_workbench(force=force, preloaded=True)`：签名没动就说明磁盘状态就是缓存那份，
  forced 重画不需要再读一遍。非 forced 的调用行为不变（原来也不会读）。
- 失败回调改成 `self.refresh_workbench_soon()`。

没碰 `apply_delta`、`_apply_row_delta`、`_paint_row`、`_queue_segment_paint`，也没碰
`source_context` / `_load_pdf`（P2-13 的范围）。

## 3 测试

`tests/qt_workbench_poll_test.py::test_a_failed_save_never_reads_the_state_on_the_gui_thread`

- 打开一个 200 段任务，`timer.stop()`；把 `adapter.submit_edit` 换成抛
  `AdapterError`；按 `threading.get_ident()` 记录 `core.load_job_state` 的调用线程；
  给 `window.refresh_workbench` 加一个记录 `force` 的透传 spy。
- 走真实链路：`submit_edit` → `flush_edits_now()` → 等 `edits_pending()` 与
  `_state_load_in_flight` 都落定。
- 断言：**GUI 线程上的 `core.load_job_state` 调用为 0**，且**仍然发生了一次
  `force=True` 的刷新**（宽度没被牺牲）。

**退回旧实现实测变红**：`git stash` 掉 `folith/qt/window.py` 后该测试
`1 failed`（GUI 线程上确实读了一次状态，栈为
`workers._failed → window.failed → refresh_workbench(force=True) → _refresh_workbench → adapter.load_state`）。
恢复实现后 `1 passed`。

本机相关套件：`qt_workbench_poll_test` + `qt_workbench_delta_test` +
`qt_setup_panel_poll_test` + `translation_save_flow_ui_test` + `qt_inline_editor_test`
**48 passed**；`qt_client_window_test` 另跑（见 PR）。

## 4 局限

- **没有新开 R 段测量**。R 段一轮是 600 s 翻译窗口（单轮约 12 分钟），本轮按任务书
  不自己开正式测量；这条改动的收益要等下一次正式 R 段复测才能量化。
  本机能给的是：该族在三轮 R 里占候选 36.9% / 基线 52.0%，以及测试钉住的
  「GUI 线程 0 次整份读状态」。
- 失败回调里 `_failure(...)` 仍然要弹一次提示，这是用户该看到的，没有改。
- 其他 `refresh_workbench(force=True)` 的调用点（译前设置保存失败、术语保存等）
  本轮**没有动**：它们不在第二轮的 `top_stacks` 里，等有证据再说。
- 没有跑 Windows 真窗口；改动不涉及平台分支。
