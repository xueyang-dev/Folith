## 结果

### 不修改即导出

四个上游文件都是 `render()` 等于原字节，`verify_export` 的 `structural_diffs` 为 `[]`。

### 改 5 个单元

`validators.en.xlf` 的前 5 个单元都有 `<target>`，且未锁定。只在译文末尾加上 ` [g4]`。不套白名单的结构 diff 恰好是这 5 条，没有第六条：

```text
changed /file:0/body:0/trans-unit:0/target:1#text
changed /file:0/body:0/trans-unit:1/target:1#text
changed /file:0/body:0/trans-unit:2/target:1#text
changed /file:0/body:0/trans-unit:3/target:1#text
changed /file:0/body:0/trans-unit:4/target:1#text
```

导出不会改状态属性，所以 diff 里没有状态节点。再解析后，这 5 个单元的 `raw_status` 与导出前相同（这份文件本来就没有状态属性）。其余单元的译文逐字符未变。套上内核既有的译文文本白名单后，`verify_export` 为 ok，`unexplained` 为空。

### 再导入

同一份改写：先 `reconcile_identities`，把前 5 个外部 id 标成已确认，再用导出字节推进同一本账。第二次的 `reassignments` 是 `[]`，`rejections` 是 `[]`，161 条身份字符串与第一次相同，且全部 `stable`。被标过的 5 条 `confirmed_state` 仍为 True，其余仍为 False。

`manual-alttrans.xlf` 的 id=3 在文件里就是确认：导入行 `reviewed` 为 True，`raw_status` 为 `approved`。只改这条译文后再导入，这两项不变，身份账本的再指派仍是 0，该实例的 `confirmed_state` 仍为 True。id=0 是 `translate="no"`，导入时排除，不在 `pairs` 里。这是原有行为，不是这次引入的。

### 多个 `<file>` 且单元 id 重复

`test1_es.xlf`：2 个 file scope，140 个单元，24 个单元 id 在两个 scope 里各出现一次，外部 id 仍是 140 个互不相同的值。`document.rejections` 为 `()`，`build_import` 的 `report.rejections` 为 `[]`，140 行全部进入 `pairs`。同一文件内部的重复 id 仍会拒绝；那条测试在 `tests/xliff12_kernel_test.py`，这次没有改它。

### 损坏节点

`derived/validators.en.damaged.xlf` 是上游文件删掉第一处 `</source>` 的结束 `>`。解析抛出的原文是：

```text
文件不可解析：XML 不可解析：not well-formed (invalid token): line 7, column 16
```

原因是 XML 不成形，位置是第 7 行第 16 列。异常类型是 `XliffStructureError`。

### 未知命名空间

`derived/validators.en.unknown-namespace.xlf` 是在上游文件第一处 `</source>` 后插入 `<vendor:note xmlns:vendor="urn:example:not-xliff">foreign</vendor:note>`。解析结果是 161 个单元，第一条源文和译文仍是 `This value should be false.`，`rejections` 为 `()`。

契约里有拒绝码 `UNKNOWN_NAMESPACE`，这条 XLIFF 1.2 解析路径不发出它。外来元素被留下，不构成一次拒绝。因此账本里「未知命名空间或损坏节点：明确拒绝」仍是**部分**：损坏节点有错误原文，未知命名空间没有被拒绝。没有为了制造这条错误去改内核。

`test1_es.xlf` 本身带有 XLIFF 1.2 以外的命名空间，同样是 0 条拒绝。这和上面的派生文件是同一事实，不是第二个结论。
