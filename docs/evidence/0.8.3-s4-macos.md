## 采样器的错（已经修，`d1b7674f`）

第一版采样器用 `pgrep -f <app 路径>` 取**最后一个 pid**。两个问题同时成立：

1. `pgrep -f` 也匹配**驱动 probe**（它的命令行里带着 app 路径）；
2. app 起来后 fork 一个 `--ui-watchdog` 子进程，**最后一个 pid 是看门狗**。

于是记录到的"峰值 50–51 MB"其实是看门狗（实测 51.7 MB），回合开始时空窗里记到的 11–12 MB 是驱动 Python；
**被测主进程（315–326 MB）从未被采到**。修法：按命令行识别「跑 app、含 `--selftest`、不含 `--ui-watchdog`」的进程，
并把 **pid + 命令行**写进每回合记录；两条测试（合成三进程夹具必须解析到主进程；无 app 时必须返回空）。
本条 RSS 数据因此全部作废，但**循环/崩溃/无响应判定不用 RSS，仍然有效**。

## G1b「空闲 RSS 不持续增长」：本次**没有证明**

这是 B-49 要求写清的：本次 8 小时是 **1141 个独立进程**，每个流程跑完就退出。跨回合的内存泄漏
**根本不会累积**到同一个进程里，所以：

- 已经证明的：**0 崩溃、0 无响应、单次流程的内存稳定（~320 MB，走平）**；
- **没有证明的**：长时间运行的**单个** app 进程不泄漏。监工的 CSV 走平也只说明"单次流程峰值稳定"，
  不是 G1b 要的那件事（每个流程结束后同一个进程里的空闲 RSS 是否持续增长）。

长活进程的验证方案见发件箱（B-49 要求先提方案、不直接跑）；判 G1b 时不应引用本文的内存数字，
只能引用"单流程稳定 + 0 崩溃 + 0 无响应"。
