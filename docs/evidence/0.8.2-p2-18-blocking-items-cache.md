# P2-18：`blocking_items` 一次打开只扫描一遍

日期：2026-11-16。分支 `fix/0.8.2-p2-18-blocking-items-cache`，基于 main `bb510009`（不 rebase）。
只改 `folith/qt/views.py` 的两个方法与两处失效点，加一条测试。

## 1 怎么找到的（P2-19 的第二步：在 `views.load` 上跑 cProfile）

单位第二次修补的起因：P2-19 的手工包装只覆盖了 `views.load` 的 20–40%，剩下 0.55 s 没拆开。
直接对 `views.load` 整棵树跑 5 次 `cProfile`（`.loop/p219/prof.py`，S3 offscreen、同一份
播种 10,000 段任务），一次打开的 profile CPU 是 **1.287 s**，前几名：

| 函数 | 调用次数（5 次打开） | cumtime | 说明 |
| --- | ---: | ---: | --- |
| `delivery.unresolved_blocking` | 25（**5 次/打开**） | 3.97 s | 每次遍历 ~9,990 条 findings |
| `delivery.finding_id` | 249,750（**49,950/打开**） | 3.13 s | 每条 finding 两次写；每次 2× `json.dumps` + 2× sha256 |
| `views.blocking_items` | 15（3 次/打开） | 2.37 s | 三个调用者各扫一遍 |
| `views.filtered_indexes` | 5（1 次/打开） | 0.83 s | 第 4 次扫描 |
| `views.blocking_count` | 5（1 次/打开） | 0.79 s | 第 5 次扫描 |

**一次打开里 `unresolved_blocking` 被调 5 次，累计 0.79 s，占打开总时长的 61%**——
P2-19 报告里「`filtered_indexes` 一次打开只 1 遍 ⇒ 缓存省不到钱」的结论只看到了 5 个
调用者里的 1 个，这里更正。

## 2 改动

`folith/qt/views.py`

- `blocking_items()` 把 `adapter.unresolved_blocking(...)` 的结果缓存在
  `_blocking_items_cached`，同一状态只算一次；返回副本，调用方改不到缓存。
- `blocking_count()` 改成 `len(self.blocking_items())`：它原来维护一个独立的计数缓存
  `_blocking_cached`，现在两者共用同一份 items，不会再各扫一遍。
- 失效点**完全沿用已有的那两个**（原来就是给 `_blocking_cached` 用的）：
  - `_replace_state()`：整状态对象换了；
  - `apply_delta()` 里「counters 变了或 review/followup/delivery 域动了」。
  两处同时清 `_blocking_cached` 与 `_blocking_items_cached`。

**失效语义写清楚**：缓存跟着「状态对象」与「这三个投影域」走。findings 的改动只有两条
路径能到达界面——整状态替换（打开、显式刷新、慢投影）或带域标记的增量——两条都在上面
清缓存。不存在「findings 悄悄变了而缓存还在」的路径。

## 3 测试

`tests/qt_workbench_poll_test.py::test_blocking_items_is_scanned_once_per_state`

- 打开一个 200 段任务，塞两条 blocking finding；
- 把 `adapter.unresolved_blocking` 换成计数器，清掉缓存后：`blocking_items()` 调 4 次
  + `blocking_count()` 一次，**只应扫 1 次**；
- 然后真的改 findings（加第三条 blocking）、`refresh_workbench(force=True)`（整状态替换），
  断言结果变成 3 条——**findings 变了，结果跟着变**。

**退回旧实现实测变红**（`git stash` 掉 `folith/qt/views.py`）：
`FAILED … test_blocking_items_is_scanned_once_per_state`。

本机：`qt_workbench_poll_test` + `qt_workbench_delta_test` + `ui_overhaul_f2_status_test`
+ `qt_delivery_supplement_test` + `task_overview_state_test` **76 passed**；
`tests/qt_client_window_test.py` **118 passed**。

连续 5 次打开大任务）在本机同一时段对跑：

| --- | --- | --- | --- |
| 一次打开的 GUI 线程阻塞 | 909 / 1,038 / 913 / 937 / 1,075（中位 **937 ms**） | 638 / 772 / 648 / 623 / 771（中位 **648 ms**） | **−289 ms（−31%）** |

## 5 局限

- 探针口径是 offscreen、单轮、25 s 窗口、n=1 对；绝对值不能与真实窗口混比。
  修前/修后在**同一时段、同一数据、同一探针**下对跑，差分可信。
- 最长单块是「被包装的步骤」里的最长；一次打开整体仍然 >500 ms，所以采样器看到的
  **次数不会变**（P2-19 已说明这一点）。
- 没有跑 Windows 真窗口；改动不涉及平台分支。
