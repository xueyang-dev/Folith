**未达到 −70%。** 口径：变化 =（候选 − 基线）/ 基线，**负数表示改善**。四格里：

## 4 与第二轮对比（同一口径）

| | 第二轮（0.8.1 → main@8 月） | 本轮（0.8.1 → e5f5941d） |
|---|---|---|
| R >100 ms | +3.9 → +4.72/min（-20.5%，变差） | 3.90 → 2.70（+30.8%，改善） |
| I >100 ms | −2% | −2.0% |
| I >500 ms | −7% | −17.6% |

R 档由第二轮的 +20.5%（变差）转成本轮的 **−30.8%**（改善），主要对应 P2-19 之后的打开路径修复。

**I >500 ms 为什么 +17.6%（只做分析，不调参、不重测）**：两种可能，
(a) n=3 的波动：cand 三轮是 22.07 / 22.96 / 22.82，**轮间只差 4%**，不像抖动，更像稳定值；
(b) 候选真的更慢：I 阶段的 >500 ms 主要由打开路径上那几次整块阻塞贡献，而 0.8.2 在打开路径上
做的修复（P2-18/P2-19 等）**减少的是单次阻塞的时长分布，不是打开次数**——打开次数在 S3 里由
脚本固定（每轮同样的切换节奏），所以如果单次阻塞跨过 500 ms 的次数没变，而 10,000 段任务在
候选上加载得更"均匀"，采样点就可能更多地落在 >500 ms 区间。**这只是解释性分析**，
要判定需要更多轮次（≥10 轮/臂）与逐观察（per-observation）数据，均已超出本轮范围。
P2-21/P2-21b 与 I 阶段无关：它们改的是采样器取帧方式与循环垃圾，不动打开路径的耗时。

### 全线程栈排行（两臂各取 total_ms 前 5，三轮合计）

进程内（`FOLITH_ENGINE_PROCESS=0`，引擎跑在 GUI 进程的 worker 线程里）：

|---|---:|---:|---:|

子进程（`=1`，引擎在独立进程，GUI 进程里只剩监督者的读线程）：

| 帧 | 次数 | 合计 | 最长 |
|---|---:|---:|---:|
| `engine_supervisor.py:533 _drain_output` | 82 | 9,950 ms | 240 ms |
| `engine_supervisor.py:580 _watch` | 81 | 9,841 ms | 240 ms |
| `job_repository.py:205 _isolated_copy` | 16 | 2,037 ms | 174 ms |
| `segmentation.py:155 _token_before` | 12 | 1,379 ms | 154 ms |
| `segmentation.py:367 _split_sentences` | 8 | 948 ms | 137 ms |

读法：进程内模式下，卡顿窗口里见到的是**引擎自己的线程**在跑（`core._runtime_heartbeat_loop`、
`trace._run_sampling` 等），最长 450 ms；子进程模式下 GUI 进程里只剩监督者读引擎输出
（`_drain_output`）与仓库的隔离拷贝，最长 240 ms。这解释了为什么"进程内"那一档的 >100 ms
略多：引擎线程与 GUI 抢同一个 GIL，卡顿窗口更容易把引擎帧算进来。
