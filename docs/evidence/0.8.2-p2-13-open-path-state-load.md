# P2-13：打开任务时不在 GUI 线程整份加载任务状态

日期：2026-11-15。分支 `fix/0.8.2-p2-13-source-suffix-state`，基于 main `243a2a66`。
改动只在 `folith/source_context.py`、`folith/qt/adapter.py`、`folith/qt/views.py`
的 `_load_pdf`，加两个测试文件里的 4 条测试。

## 1 现象（来自 P1-5 第二轮的原始数据，不是本机新测）

第二轮 S3（只测 I，10,000 段已完成任务）的两臂 `metrics.gui_jank_process.top_stacks`
里，**第一名是同一条栈**：

```
window.py done → _apply_open_job → views.py load → _load_pdf
→ adapter.source_context_available → source_context.has_streaming_source
→ source_context.source_suffix → core.load_job_state
→ job_repository.load_job_state_cached → _isolated_copy
```

| 轮 | 候选 | 基线 |
| --- | --- | --- |
| s3-*-1 | 19 次 / 20,243 ms / 单次最长 1,134 ms | 18 次 / 19,696 ms / 1,168 ms |
| s3-*-2 | 19 次 / 20,651 ms / 1,187 ms | 18 次 / 20,086 ms / 1,220 ms |
| s3-*-3 | 19 次 / 20,864 ms / 1,268 ms | 18 次 / 20,406 ms / 1,324 ms |
| 三轮合计 | **57 次 / 61,758 ms（占全部采样停顿的 57.2%）** | **54 次 / 60,189 ms（51.3%）** |

机制：`source_context.source_suffix()` 只需要任务状态里的 `filename` 一个字段，却
自己调 `core.load_job_state()`——一次 30 MB 状态的反序列化 + 安全深拷贝。而调用方
`views._load_pdf` 手里**已经**有 `self._state`（`load()` 里 `_replace_state(state)`
在这之前执行），那份状态是打开任务的 worker 线程刚读好的。

## 2 改动

- `folith/source_context.py`
  - 新增纯函数 `suffix_from_filename(filename)`：文件名 → 流式后缀，不读状态。
  - `source_suffix` / `has_streaming_source` / `source_kind` / `load_blocks` /
    `locate_segment` 都加可选 `state`。**给了 `state` 就只读 `filename`，不再
    `core.load_job_state`；不给才回退读盘**（后台线程、冷路径、测试用）。
- `folith/qt/adapter.py`：`source_context_available` / `source_document_blocks` 接受
  并转发 `state`；`segment_source_context` 把它一路传给 `source_kind` /
  `locate_segment`（顺带把「查看原位置」这次用户动作里重复的两次状态读盘去掉）。
- `folith/qt/views.py` `_load_pdf`：把 `self._state` 递进去。`self._state` 不是 dict 时
  传空 dict，**故意不传 `None`**：`None` 会走回退读盘，而回退读盘不该出现在 GUI 线程
  的打开路径上。
- 没有碰 `_poll_workbench*`、`apply_delta`、`_apply_row_delta`、`_paint_row`、
  `_queue_segment_paint`，也没有碰 Worker B 的 #426 文件。

## 3 测试

`tests/source_context_test.py`

- `test_availability_uses_the_state_the_caller_already_has`：带 `state` 时
  `source_suffix` / `source_kind` / `has_streaming_source` / `load_blocks` /
  `locate_segment` 一次 `core.load_job_state` 都不调；不带时仍回退读盘（行为不变）。
- `test_a_state_without_a_streaming_filename_says_no`：非流式格式直接说没有。

`tests/qt_source_panel_test.py`

- `test_adapter_availability_takes_the_state_it_is_given`：适配层同样不自己读状态。
- `test_opening_a_task_never_reloads_the_state_on_the_gui_thread`：真正的钉子。
  跑真实打开流程（`selftest.open_job_and_wait`），用 `threading.main_thread()`
  过滤，断言 **GUI 线程上 `source_context.source_suffix` 收到的 `state` 都不是
  `None`，且 GUI 线程上 `core.load_job_state` 调用 0 次**。

**退回旧实现变红（已实测）**：`git stash` 掉三个实现文件后

```
FAILED tests/source_context_test.py::test_availability_uses_the_state_the_caller_already_has
FAILED tests/qt_source_panel_test.py::test_opening_a_task_never_reloads_the_state_on_the_gui_thread
2 failed
```

红的点是 `assert all(state is not None for state in gui_calls)`——旧实现的
`_load_pdf` 不递状态，`source_suffix` 收到 `None` 就去读盘（同一测试的
`gui_loads == []` 也会红）。恢复实现后两条都绿。

## 4 对照（只跑 S3，offscreen，两臂各 1 轮 × 两个顺序）

不是正式测量，不用来替代任何官方数字。两臂**只差 P2-13 这一处**，复用同一份播种
10,000 段任务（`883df50d075425c6`，`segments=10000`，源文摘要
`sha256:f83fa42dc41f2fd9`，与第二轮证据同一份）。命令：


## 5 顺带核查过的两件事

### 5.1 为什么 GUI 线程上这一次读状态是 1.1 s，而 worker 线程上同一个调用只要 60–91 ms

`open_job` 的 worker 线程里 `adapter.load_state` 的阶段耗时（`logs/qt-client.log`）
两臂都在 60–91 ms（我的微基准：热态 169–176 ms，冷态 436 ms，30.4 MB）。
GUI 线程上同样的调用却采样到 1,071–3,358 ms。**同一个调用，差一个数量级。**
本轮**不归因**，只记录可检验的假设：GUI 线程做这次深拷贝时，活对象图（当前
`_state`、rows、widget）比 worker 线程大得多，深拷贝产生的大量分配会把 Python 的
分代回收推到 gen2，扫描整张活对象图。

这条假设也解释了第 4 节里停顿换位置：旧实现那次深拷贝顺带当了一次 GC 触发点，
现在没有了，同样的回收被推迟到后面的 `finding_id` / `flow_layout` 分配上。
**验证方法（下一轮，不用重跑正式测量）**：`gc.callbacks` 打点记录
`phase/collected/generation` 与时间戳，跑同一份 S3 offscreen 一轮即可确认停顿是否
落在 gen2 回收上；必要时对照 `PYTHONMALLOC=malloc` 与 `gc.freeze()`。

### 5.2 `has_pdf_source` / `has_streaming_source` 里的 `core.load_source` 是不是同类开销

不是同一量级，本轮**没有改** `folith/pdf_preview.py` 和 `core.py`（不在改动范围内），
另开节点 P2-14。

- 第二轮 S1/S3 的 fixture 两臂都是 **EPUB**，播种任务的 `source.bin` 只有 **1,163 B**。
  本机微基准：`core.load_source` 0.97 / 0.12 / 0.13 ms，`has_pdf_source` 对 20 KB 的
  PDF 是 0.05 ms。相对 170–1,130 ms 的状态加载小三个数量级，所以在第二轮的
  `top_stacks` 里看不到它。
- 但对**真实 PDF 任务**，同一个打开路径会把 `source.bin` 整份读两遍：`_load_pdf`
  里的 `pdf_available`（`source.startswith(b"%PDF")`，其实只要头 5 个字节）和紧接着
  `pdf_panel.load` 的 `pdf_page_count`（`fitz.open` 整份）。20 KB 的 PDF 上
  `pdf_page_count` 实测 6.8 ms 冷 / 0.2 ms 热；扫描版 PDF 常见 20–50 MB，
  按字节数线性放大。
- 因此：**不是第二轮的头号同类开销，但是真实 PDF 任务上的同类机制**，第二轮没有
  覆盖（fixture 是 EPUB）。建节点 P2-14，不并入 P2-13。

## 6 局限

- 对照是 **offscreen、每臂 1 轮 × 2 个顺序**，不能替代真实窗口的正式测量，
  也不进任何门槛；绝对值不能和第二轮的 macOS 真实窗口数字混着比。
- 两个顺序的 I>100ms 一个降一个升，说明 n=1 的差分只在“这条栈消失 / 换了位置”
  这件事上可靠，比率上的小差异不可靠。
- 停顿换位置**机制未归因**（5.1 是假设，不是结论）。
- 没有跑 Windows；改动不涉及平台分支，测试在 Windows CI 上应当照跑
  （只用 `threading.main_thread()` 与 `QT_QPA_PLATFORM=offscreen`，都是跨平台的）。
