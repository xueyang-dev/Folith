## 3. 分阶段算法（照 §5.4）

报告文件里有两个窗口：

- **场景窗口** `metrics.gui_jank`：从 `jank.checkpoint()`（导入之前）到运行结束。
- **运行窗口** `metrics.run_records[0].gui_jank`：任务自己的那次运行（翻译开始→完成）。

```
R（翻译中）>X ms 次数/分钟 = 运行窗口 >X ms 次数 ÷ 运行窗口 observed_s × 60
I（完成后）>X ms 次数/分钟 = (场景窗口次数 − 运行窗口次数) ÷ (场景窗口 observed_s − 运行窗口 observed_s) × 60
I 阶段时长 = 场景窗口 observed_s − 运行窗口 observed_s
I 阶段短于 15 秒的轮次作废
```

`>100 ms` 用 `slow_count`，`>500 ms` 用 `severe_count`；两者都不含 `instrumentation_*`
（采样器自报的工具内卡顿）。中位数取每组 5 个有效轮次。**本次作废 0 轮**：13 个
JSON 的 I 阶段时长为 48.30–50.24 秒，全部 ≥ 15 秒。

说明：按上面的定义，I 阶段包含导入窗口。本次导入 + 收尾合计仅约 0.5 秒（场景窗口
60.5 秒 − 60 秒交互），对 I 的影响可忽略。运行窗口只有 10.2–12.2 秒，因为 mock 网关
瞬时返回、1000 段在 11 秒左右译完；这与计划 §5 表里"翻译耗时 26–28 秒"不同，见 §9。

## 10. 机制层核对（只用于解释，不改变上面的判据）

1. **#344 自带的回归测试在 B 树通过。** 在 `/tmp/p0-5v/B` 跑
   `pytest tests/qt_workbench_domain_versions_test.py -q -k "unchanged_refresh or replace_state or plain_attribute or static_check"`
   → `4 passed, 11 deselected`（含 `test_unchanged_refresh_keeps_domain_versions_and_skips_projections`）。
   `python scripts/check_workbench_domain_cache.py` → `OK: no state-identity cache keys`。
   也就是说，"状态未变的刷新不再让 12 个域各加一"这条**在单元层面确实修好了**。
2. **端到端的刷新路径仍然更贵。** 按 `top_stacks` 里带 `refresh_workbench` 的栈统计
   （整个场景窗口）：
   - A：107 个事件、阻塞合计 39 723 ms（每轮约 7 945 ms，单事件均值 371 ms）；
   - B：99 个事件、阻塞合计 48 745 ms（每轮约 9 749 ms，单事件均值 492 ms）。
   事件数少 8%，阻塞时间多 23%，**单次刷新长 33%**。这与"同一路径每次多做一点活"
   的特征吻合：>100 ms 略降、>500 ms 明显上升、总阻塞时间只多 5%。
3. **一个具体的剩余路径（假设，未证）。** B 的 `_render_delivery` 缓存键新增了
   `self._domain_version("delivery")`（`folith/qt/views.py:6319`），而 `main` 的键是
   `(job_id, len(snapshots), delivery_status)`（`folith/qt/views.py:6247–6259`）。
   于是任何 bump 了 `delivery` 域的 delta（完成后的人工编辑流每隔约 1.2 秒一次）都会
   让交付面板重算：栈里可见
   `views.apply → _render_delivery → adapter.delivery_preview → validate_translation_pairs
   → check_translation_batch → script_leak`，1000 段时单次 400–580 ms。`main` 在同一条
   路径上因为键里没有域版本，快照数与交付状态不变时直接命中缓存。
4. **另一个候选。** `apply_runtime()` 现在每次 1 秒 tick 都会
   `self._bump_domains(("runtime", "stage"))`（`folith/qt/views.py:4137`），`main` 没有
   这一步。量级应当远小于第 3 条，但属于同一类"新增的每 tick 失效"。

这两条都只作为"下一步该看哪里"的线索，**没有**用修改后的代码反向验证，不能当成结论。

## 12. 这些数字不能当什么

**这是 offscreen + mock 负载 + 源码构建的诊断数据。**

- 不是冻结版（`--mode source`，`real_machine_baseline: false`）；不是真实窗口系统
  （`QT_QPA_PLATFORM=offscreen`，没有合成器、没有 GPU 绘制路径、没有原生输入）；
- 不是真机验收，GPU、字体、电源状态、外接屏都与真实使用不同；
- mock 网关瞬时返回，翻译阶段只有约 11 秒，与真实模型延迟下的运行时序不同；
- 驱动脚本本身是最大的卡顿来源：每轮 `driver_only` 栈 28–40 个事件、均值 168–229 ms
  （`runtime_baseline_runner.py:310/335 in _interact`，栈下没有产品帧）。这正是
  #347 要修的东西；绝对卡顿率被工具放大了，**因此本文件不能作为 G2 门槛证据**，
  只能作为"同一工具、同一参数下的 A/B 相对对照"。
