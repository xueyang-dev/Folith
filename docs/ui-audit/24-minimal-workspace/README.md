# Folith / 译页 极简工作台 UX 审计

审计结论：`needs revision`

报告复核版（2026-09-19）：核心任务工作区整改方向成立；本报告覆盖主要页面和部分任务状态，不代表全项目所有流程已完成验证。以下已区分截图观察、代码事实和待验证的设计建议。原 P0/P1 编号调整为稳定的 UX 编号，避免把视觉优先级误称为事故严重等级。

本轮审计针对用户提出的目标：任务打开后直接进入翻译工作台；任务概览不再作为独立页面；重要信息压缩成任务 Banner 内的极简 indicators；页面减少重复状态、重复 CTA 和无意义留白。

## 主要判断

当前视觉问题不是单个卡片的圆角或颜色问题，而是信息架构仍然以“概览页”为中心。任务状态被同时渲染在 Banner、工作台工具栏、翻译正文状态条、Inspector 和概览卡片中，导致用户需要重复阅读同一组数字才能决定下一步。顶部 Banner 下方的“查看概览”又把用户带回这套重复结构，抵消了“翻译工作台是首页”的设计目标。

建议把任务页收敛成一条身份与状态 Banner、一个轻量工作台工具栏和一个当前任务页面。Banner 集中展示全局状态摘要；正文只展示当前页面必须理解的局部状态。

## 问题记录

### UX-01：概览页重复了 Banner、翻译页和交付页的同一组信息

证据：[04-overview-current.png](04-overview-current.png)。顶部已经显示“可以准备交付”、82/82 段、38 术语、8 项发现和“准备交付”；工具栏又显示状态 chip；概览页再次显示状态 Hero、准备交付按钮、24 项建议、翻译卡片、交付卡片和项目进度。概览页承担的只是把同一状态重新排版。

代码位置：`app.py:8660-8731`、`app.py:9675-9825`、`app.py:12783-12810`。

整改：删除概览导航、`查看概览` 按钮和 `_render_workspace_overview` 路由。保留 Banner 内的一组指标和一个主 CTA；指标点击进入对应页面，发现指标进入问题抽屉或审校页。不得再渲染第二套“状态 Hero + 阶段卡片 + pipeline”。

### UX-02：全局状态展示重复，但不等于底层状态计算不统一

证据：[03-workbench-current.png](03-workbench-current.png)、[13-review-blocker-workbench-home.png](13-review-blocker-workbench-home.png)。Banner 与工具栏重复全局交付判断；翻译指标行重复部分任务指标。Inspector 还包含当前段的状态，必须与全局状态区分，不能一并删除。审校阻塞任务甚至同时有 Banner CTA、工具栏 warning、Inspector “必须处理”和“查看审校”。

代码位置：`app.py:8735-8855`、`app.py:10137-10281`、`app.py:9643-9673`。

整改：工具栏只保留当前页面导航，不再放 canonical status chip；翻译页去掉全局指标行，只保留段落筛选和局部段落状态。Banner 保留全局摘要；复用现有 `_task_overview_state` 的交付判断和 `_planner.workspace_progress` 的各维度计数，不新建第二套状态计算。当前 shell 已把同一 overview 传给 Banner 和导航，因此已确认的是展示重复，并未证明它们数据源冲突。当前段审校状态、未保存标记和局部问题提示继续留在编辑区域。

### UX-03：删除概览后，运行中断、恢复、取消和重试动作不能丢失

代码事实：`_render_runtime_panel` 在 `app.py:8506-8580`，当前只由概览页在 `app.py:9690` 调用；它承载取消任务、继续处理、放弃当前运行和重试当前步骤。

整改：把运行状态放入 Banner 的状态 indicator。点击 indicator 展开轻量运行详情 popover，显示进度和最近事件；当前可执行的恢复/重试作为可见主动作，取消作为运行中的次要动作，不要求用户先打开 popover 才能恢复任务。不要用一个新的大卡片替代概览页。`folith/task_overview.py:510,522` 中指向 `overview` 的恢复 CTA 要改为 Banner 运行详情或实际目标页面。

### UX-04：任务历史卡片信息密度低；fixture 标题不足以证明真实任务命名缺陷

证据：[02-history.png](02-history.png)。卡片高度远大于内容，右侧只有一个按钮，左侧散落标题、类型、状态、段数、项目和时间。多个 fixture 显示“未命名任务”。复核 `folith/history_view.py:186` 后确认：代码已有显式名称、文档画像名称和文件名回退，且有意隐藏 audit 内部标识。因此此现象仅证明测试数据缺少可读名称，不足以判定真实文档的命名有缺陷。未完成任务的“最近更新”还会在卡片内和卡片外重复。

代码位置：`app.py:13195-13318`。

整改：改成紧凑任务行：文件/章节标题 + 一个状态 chip + 2–3 个指标 + 单一下一步 CTA。保留现有可读标题优先级，以实际文档验证标题；为截图 fixture 补充可读名称；文件名放入可点击的任务详情，不能只靠 hover 获取；删除卡片外重复的最近更新时间；整行“打开任务”可进入翻译，明确标注的“继续审校”等 CTA 可进入对应工作，两者不必同路由；只去掉重复同名入口，并验证焦点、点击范围和键盘激活。

### UX-05：翻译工作台仍有三条全局进度叙述

证据：[03-workbench-current.png](03-workbench-current.png)。Banner 有 82/82，翻译标题右侧又有进度条 82/82，下面还有“翻译 82/82、术语已确认 0/38、审校、发现”一行；这让翻译数字看起来比其它维度更重要，也把正文向下推。

代码位置：`app.py:10137-10281`。

整改：Banner 内保留“翻译 82/82”小 indicator；正文从搜索、筛选和段落列表开始。进度条只在确实存在处理中状态时显示，完成态使用一行静态文本即可。

### UX-06：翻译 Inspector 的诊断动作会错误地提供“应用到译文”

代码事实：`app.py:9363-9392` 明确要求“术语检查”和“上下文一致性”只输出诊断，不输出改写；但 `app.py:9406-9421` 对所有 suggestion 无条件显示“应用到译文”，并把 `suggestion["text"]` 写回正文。

整改：将 Agent 结果分为“诊断”和“改写候选”两种类型。诊断只展示问题、定位和建议；只有明确的改写候选显示“应用”。自定义指令可能请求解释或诊断，也不能默认视为可写回译文。先修复类型限制，再复用现有候选预览；差异对比可单独迭代。这个问题属于内容安全和信任风险，优先级与视觉精简同等重要。

### UX-07：术语工作台和交付页仍有过多空白和全局状态重复

证据：[05-terms-workbench.png](05-terms-workbench.png)、[06-delivery-workbench.png](06-delivery-workbench.png)。术语页右侧详情栏在未选中或信息很少时占据整列；交付页再次显示 Banner 的“可以准备交付”，然后用一个大面积 checklist 重新解释所有未启用能力。

代码位置：`app.py:10281-10670`、`app.py:12351-12670`。

整改：术语页无有效选择时不占用固定详情列；选中后的桌面布局优先复用现有详情列，窄屏改为按需展开区。独立 drawer 作为备选方案，先验证 Streamlit 实现成本和焦点行为；空详情不占列。交付页保留门禁清单，但改成“检查结果 + 唯一下一步”结构，未启用的能力收进“检查范围”折叠项，不要每项重复一段“当前任务未启用”。

### UX-08：新建任务 Step 1 的卡片固定高度制造空白

证据：[01-new-task.png](01-new-task.png)。目标语言、项目上下文、术语库和智能画像四个卡片的内容量差异很大，却被同一高度撑开；左侧四步导航和右侧表单同时占据首屏。

代码位置：新建任务四个设置卡的直接规则为 `app.py:4545` 附近的 `.st-key-task_setting_*`（`min-height:142px`）。`.tp-summary-card/.tp-stage-card` 和策略卡是其它布局规则，不能据此认定它们造成 Step 1 留白。

整改：卡片高度由内容决定，统一使用更小的 section padding；Step 1 只保留文件、目标语言和项目上下文，术语库/智能画像改为“可选设置”折叠区。下一步按钮先放在表单结束位置；仅当长表单确有可达性问题时采用吸底栏，并验证不会遮挡内容。减少四步导航的视觉权重。

### UX-09：项目内摘要存在潜在重复；空项目留白不是独立缺陷

证据：[07-project-center.png](07-project-center.png)、[08-project-detail.png](08-project-detail.png)、[09-project-knowledge.png](09-project-knowledge.png)。项目中心有系统任务区和项目卡片，项目详情又有概览、任务、项目知识、设置四个层级；空项目详情只有一张大卡片，页面下方大面积空白。知识页四个空模块纵向重复“暂无内容”。

代码位置：`app.py:13963-14450`、`app.py:14687-14890`、`app.py:14914-15125`。

整改：保留项目中心的未归属任务入口，不能因精简项目卡片而让任务失去归属入口。项目详情默认任务列表作为设计建议，在含多个真实任务的项目中验证后实施；删除任务概览不等于必须删除跨任务的项目概览。代码显示“进行中的任务”与“最近任务”可能包含相同任务，可先消除重复行。空项目已具备创建任务与设置知识动作，页面剩余空白可接受；只压缩控件内部无意义占位。知识全空时使用一个空状态，不新增四个零值指标。

### UX-10：项目设置把简单信息拆成大块卡片

证据：[10-project-settings.png](10-project-settings.png)。项目资料、状态、高级信息分别占据大面积白卡，实际可编辑内容很少；高级信息中的 ID、UUID、创建时间对常规任务没有帮助。

代码位置：`app.py:14778-14890`。

整改：名称与描述放入同一表单分组，描述保留多行编辑；可逆归档作为低频状态动作放在页面底部，不必渲染成危险告警；高级 ID 默认折叠，不在首屏占据一个大卡片。

### UX-11：尚未开始的任务出现空白工作台，下一步只在 Banner

证据：[14-runtime-incomplete.png](14-runtime-incomplete.png)。正文只有“翻译尚未开始”的大虚线区域，右侧 Agent 只重复“尚未开始”，页面大部分留白。用户真正要做的是点击“开始翻译”。

整改：开始动作仍只保留在 Banner；正文使用简短状态说明，仅展示已知前置条件与真实缺失项，不再增加第二个开始按钮；当没有任何段落时不渲染翻译表格和 Inspector 空卡片。

## 目标信息架构

```text
全局侧栏
├─ 新建任务
├─ 项目
├─ 历史任务
├─ 术语与翻译记忆
└─ AI 引擎设置

任务工作区
├─ 任务 Banner
│  ├─ 文档身份
│  ├─ 小型 indicators：翻译 / 术语 / 审校 / 发现 / 最近保存
│  └─ 一个主 CTA：当前推荐下一步
├─ 工作台工具栏
│  ├─ 翻译
│  ├─ 术语
│  ├─ 审校（仅启用时出现）
│  ├─ 案例 / 报告 / QA（仅启用时出现）
│  └─ 交付
└─ 当前页面正文
```

“概览”从导航和路由中移除。Banner indicators 是全局状态的集中摘要入口；点击“发现”打开问题抽屉，点击“审校”进入审校，交付操作进入交付页。运行中的取消、恢复、重试动作放在 Banner 状态区域，详细日志按需展开，不能因为删除概览而丢失。

## 分阶段整改方案

### 第一阶段：任务工作区与功能回归保护（优先施工）

1. 迁移 runtime panel 的恢复/取消/重试动作到 Banner 状态区域，详细日志按需展开。
2. Banner 改为一行身份 + 一行小 indicator；删除 toolbar 的 canonical status chip。
3. 删除 overview tab、`查看概览`、overview hero、overview stage cards 和 pipeline。
4. 把 `task_overview` 的显式 action destination 从 `overview` 改为实际目标页面，并补齐运行状态测试。
5. 修复诊断 suggestion 不得直接覆盖译文的问题。

验收：普通打开任务默认进入翻译；有段落时首屏出现可编辑内容，无段落时出现原因与明确下一步。带“继续审校”等语义的上下文入口允许直达对应页面。全局摘要集中于 Banner，局部状态按上下文保留；中断可恢复、失败可重试、运行中可取消，操作后反馈可见。

### 第二阶段：压缩任务列表和内容页

1. 历史任务改为紧凑行，去掉重复更新时间；验证真实文档标题，不把隐藏内部 fixture 标识的回退当作故障。
2. 翻译页移除全局进度重复行，只保留当前段和筛选工具。
3. 术语页使用按需详情，交付页将未启用检查折叠。
4. 尚未开始/无段落状态改为简短说明与 Banner 主动作，不渲染空 Inspector。

验收：1440×900、有段落的翻译页面中，首段起始位置目标位于视口顶部 360 CSS px 以内（高度的 40%），不要求长段落完整显示。Banner 中的同一全局指标只常驻一次；当前段术语数量、筛选命中数和交付门禁内的解释性数据可以保留。主动作无需滚动即可发现。该几何目标是待截图验证的设计目标，不是当前测量结论。

### 第三阶段：验证后统一项目与新建任务密度

1. 新建任务卡片改为内容高度，Step 1 减少为必填内容 + 可选设置。
2. 项目中心保留项目导航、创建和未归属任务入口；用有任务项目验证任务列表作为默认页。
3. 空项目、知识、设置页面改为 compact empty state 和折叠高级信息。

验收：相同空状态不重复说明；保留自然留白，去掉控件固定空高度；任务身份、状态和动作语义一致，布局可根据全局列表与项目列表的上下文调整。

## Banner 的具体设计约束

Banner 使用紧凑两行：第一行文档标题、当前状态和自适应宽度的主动作；第二行是低视觉权重的文字指标。不要给每个指标再包一个独立白卡，也不让按钮拉伸填满整列。长标题允许截断，但完整标题/文件名可通过任务详情查看与复制。

| 信息 | 展示规则                             | 操作或含义                    |
| -- | -------------------------------- | ------------------------ |
| 翻译 | `已译 82/82 段`                     | 表示译文覆盖，不代表已审校或可交付        |
| 术语 | 需要确认时 `术语已确认 0/38`；只供参考时 `术语 38` | 进入任务术语；总数与确认数不能混用        |
| 审校 | 仅适用时显示当前有效结果/待处理数                | 不适用收进任务详情；过期结果不能算完成      |
| 问题 | 明确区分 `必须处理 N` 与 `建议 N`           | 打开已有问题面板并按类型筛选；参考信息可收进详情 |
| 保存 | 常态低权重 `已保存`；未保存/失败明确提示           | 不把最近一次磁盘保存误称为当前输入已保存     |
| 运行 | 运行中/中断/失败在主状态区显示                 | 恢复与重试可见；详细日志按需展开         |

当前截图里的“8 项发现”和“24 项建议”未证明是同一计数口径。实施前必须核对来源和统计单位（问题条目/命中位置/交付检查项），不能因为视觉精简直接合并；正文指标迁入 Banner 时复用已有语义。零项必须处理不需要常驻红色或警告样式。

## 实施约束与验证矩阵

- 保留现有状态派生、交付门禁、问题面板和段落定位能力；删除的是概览界面，不是 `task_overview` 的业务判断模块。
- 先迁移运行控制并验证动作，再在同一轮改动中删概览。清理所有导航、空状态中的“回到概览”提示、session 入口和相关测试；旧 session 的 overview 值使用现有非法页面回退到翻译即可，无需另建迁移框架。
- 布局调整优先复用当前 Streamlit 组件和 CSS，按需详情先不承诺新 drawer 系统。首次施工集中于 UX-01/02/03/05/06/11；项目级导航属于后续验证范围。
- 验证任务状态：未开始、运行中、中断、失败、部分翻译、译完未审、审校过期、存在阻塞、仅建议、可交付、已交付后译文变更。只使用能够构造的真实状态；无法复现时明确记录。
- 行为验收：诊断不能写回；改写经用户应用才保存；指标进入正确页面/筛选；定位问题保留选中段并在必要时放宽筛选；刷新后导航与任务状态合理；自动轮询不丢输入、焦点或反复滚动。
- 视觉验收：1440×900 与 1024×768 桌面、窄窗口及 200% 缩放。宽屏保留原译对照，窄屏允许切换或堆叠；页面不产生意外横向溢出，正文表格的必要滚动可单独保留。
- 可访问性：indicator 若可点击必须用可键盘操作的控件，有明确名称与焦点；非交互指标不伪装按钮；颜色旁保留文字，缩小视觉占位不等于缩小点击范围；详情关闭后焦点返回触发点。

## 复核结论与保留项

已确认：概览重复、全局指标重复、概览承载运行控制、诊断可被应用到译文、历史重复更新时间、Step 1 设置卡固定最小高度。

需要限定：Inspector 的局部状态不属于冗余；空页面自然留白不属于故障；fixture 的未命名标题不能代表正常文档缺陷；项目概览是否保留需看跨任务用途；全局任务入口和任务内 CTA 可以有不同但清楚的去向。

值得保留：默认打开翻译、原译并排编辑、段落 Inspector、已有问题定位面板、共享交付判断、历史搜索筛选与项目知识分类。整改应减少阅读和操作负担，而不是尽可能塞满首屏。

### 实现约束与代价

- 运行控制的归属由 `_RUNTIME_ACTION_STATUSES` 判定：运行区会给出自己的主动作时，Banner 不再渲染第二个 canonical 主动作按钮（否则同屏会出现两个「继续处理」）。`waiting_manual` 这类"运行区不提供按钮"的状态仍然保留 canonical 主动作。
- `_render_runtime_strip` 全部按 `.get` 取值：报告页的状态卡会注入裁剪过的运行视图，缺字段必须退化成"不渲染"，不能 KeyError 打掉整页。
- `derive_task_overview_state` 的 `resume` 动作落点由 `overview` 改为 `translation`；`history_view.CTA_DESTINATIONS` 中「查看进度 / 继续处理 / 打开任务」同样改为 `translation`。
- 「任务详情」保持 `st.expander` 而不是 `st.popover`：Streamlit 1.63 的 AppTest 读不到 popover 内容，换成 popover 会让"完整文件名可读可复制"失去回归断言。代价是要用 CSS 把这个展开器从 38px 的默认摘要压成 30px 的 chip（`.st-key-workspace_task_details`）。
- 概览页专用 CSS（hero / stage-card / pipeline / capability / canonical chip / 运行时面板骨架）已一并删除，共 97 条规则；`tp-cat-metric` 随四维指标行一起退役。

### 留给后续阶段的发现

1. **`h2` 的 padding 泄漏在另外 8 处仍然存在**：术语（`app.py:10169`）、审校工作台（`10484`）、
   案例终审（`10723`）、合规与最终 QA（`10989`）、报告（`12185`）、最终交付（`12420`），
   以及项目页的两处空状态标题（`14157` / `14164`）。它们连作用域规则都没有——本该管这件事的
   `.tp-workspace-main h2 { margin:2px 0 5px; font-size:21px !important }`（`app.py:3155`）
   是一个**从未被渲染的死选择器**（`tp-workspace-main` 在渲染代码里不存在）。所以这 6 个
   分区标题实际吃的是全局 `h2 { font-size:23px !important }` 加上 Streamlit 的默认 padding。
   属于 UX-07 / UX-09（第二、三阶段）；本轮不混进来是因为它会让改动无法按单一原因回归。
2. **中断态下 Banner 把状态说了两遍**：canonical verdict 显示「处理中断」，紧跟的运行区
   又显示「上次运行已中断」。两者语义不同（业务态 vs 运行态）且运行区还携带进度与动作，
   因此没有合并；继续压缩时这是第一个候选。
3. **`_RUNTIME_ACTION_STATUSES` 是硬编码清单**：新增运行状态时必须同步维护，
   否则同屏会出现两个「继续处理」。
