# Folith 真实翻译任务性能审计

2026-10-08。覆盖最近 5 个有真实 API 调用的业务文档任务，另列 1 个验证样本。合并桌面数据与旧版 `outputs`，按 job_id 去重、最近运行启动时间排序。没有修改生产代码、任务状态或翻译质量策略。统计表及可复现证据见 [metrics.md](metrics.md)、[analysis.json](analysis.json)、[evidence.json](evidence.json)；复现入口为 [audit.py](audit.py)。

结论：最显著的三个瓶颈是长文档的串行自动标注、翻译流水线中的多轮模型调用与串行知识反馈、失败及恢复造成的额外历时。正常状态写入的已测耗时很小；但是历史磁盘写入失败确实中断过任务。当前日志不能精确计算实际 HTTP 并发、各子阶段独占关键路径时间或最终交付耗时。

## 最主要的三个瓶颈

### 1. 长文档的串行自动标注

**实测：** Sensorium 的标注独占后续时间线 3,188 s，占端到端 43.13%，比整个翻译循环的 3,295.760 s 几乎同样长；65 批逐次返回。Sky 的最后标注 run 需要 3.39 小时。即使译文已经完成，后续加工仍显著延迟 worker 完成。

**代码佐证及推测：** 当前 `core.py:annotate_stage` 是逐批循环调用模型，日志也符合串行模式。文档段数增加会增加批数和等待次数；但无法仅靠当前版本代码证明历史版本的每一条 HTTP 请求调度。未进行关闭标注或改变标注质量的试验，不把可能收益写成实测。

### 2. 多轮模型调用、小批正文与串行知识反馈共同限制翻译吞吐

**实测：** Attention-2p 的 22 个计划批次产生 68 个逻辑调用，Attention-8p 的 89 批产生 275 个；分别约 3.09 次调用/计划批次，包含术语等辅助调用，不能称为每个生成请求一定重试三次。两者 review 账本分别有 26、108 次调用，多于 22、89 批。生成之外还有修复、复核及辅助调用。

Sensorium 的知识反馈累计 3,179.449 s，接近翻译循环 3,295.760 s 的 96.47%。当前代码把 `observe_batch` 放在主提交路径，而 batch worker 可以继续生成/审校；因此其累计时长对该循环是很强的串行下界证据，不能把其余生成累计耗时也加上。Attention-2p/8p 的知识反馈分别为 256.436/766.850 s，占循环约 64.1%/74.5%。正常 state_commit 小于 1 s，不能把这些远程等待归咎于状态落盘。

各任务批上限是 4 段/2,400 字符，但已提交 packet 的当前正文平均仅约 160（2p）、254（8p）、648（53p）、286（224p）字符；2p 的 22 批中有 10 批只有 1 个待模型处理段、2 批为 0。这里包含 TM/复用效果，不能视为分批错误或批上限一定配置不当。

**重复上下文实测代理：** Sensorium 累计前缀 557,934 字符，当前正文 108,161 字符，前缀/正文 5.16 倍，前缀占 packet 83.0%；Sky 对应 5,060,150/348,781 字符，14.51 倍、92.8%。2p/8p 则为 3.94/3.05 倍。模型每次携带的内容中，辅助上下文比例很高。这不是 tokenizer 精确成本，也没有统计完整 system prompt、审校 prompt 和所有重试。

**推测：** 多轮调用和小正文批次会反复支付网络、模型生成及上下文处理成本，串行反馈可能使 worker 的已完成结果等待提交。输入开销较高不等于所有上下文冗余；这些上下文承担质量策略，报告不建议直接删减。缺少精确重复组件和 provider 缓存命中信息，无法量化可消除成本或给出最佳批大小。

### 3. 请求长尾、运行故障与恢复使历时扩大

**实测：** Eco 首次 run 212 个逻辑调用中 63 个失败，P95 55.804 s、最大 253.823 s；技术日志指出 APIConnectionError，最终仅到 223/445 个已存 pairs，之后恢复并取消。Sky 首次 run P95 247.401 s、最大 328.651 s，连接错误 57 次；其后出现磁盘空间不足、runtime_state 临时文件 rename 失败和 403 余额不足。余额不足的两个已存 run 合计 112 个失败调用（58+54），其中一个 10.787 s 的 run 是 54/54 调用全失败。

Sky 已存 6 个 run 中 5 个 failed；runtime_events 有 9 个 worker_started，只有 6 个 run summary，另有嵌入 profiler 对应 `run_20260930_154304_98256212` 却没有对应 run 汇总。最后 `completed` run 仍有 54 个失败调用，状态记录标注失败 55/485 批。不能以 worker 成功抹去这些失败，也不能把失败调用的全部运行时长算作“浪费”，因为失败 run 也保存了有效译文。

**推测和限制：** 故障后恢复造成的等待和可能重做增加端到端历时，但没有稳定请求/批次/尝试关联，无法精确计算重复请求、丢失工作或某一个故障的额外秒数。临时文件错误的根因不能仅凭日志确认；旧任务存在多个 worker 启动，缺少完整退出关联，不能认定当前生产版本必然仍有同样问题。

## 限流、重试、并发和请求分布

实测请求延迟分布、失败数、输入/输出/缓存 usage 全部逐 run 列在 metrics.md；原始汇总还有 P90/P99，保存在 evidence.json.runs.latency_percentiles。没有把各 run 的 P95 再求平均当总体 P95，也没有从批次除以段数伪造逐段 API 延迟。

所有已存 run 的 `errors_and_retries.retries=0`，但 Eco 有 33 条 `translation_retry` 事件、Sky 有 34 条。因此零是计数通路缺失，不能解释为无重试。当前代码中翻译调用可进行三次外层尝试，SDK 配置还有内部重试；日志缺少每个 HTTP attempt 和 backoff。无已存明确 429/RateLimitError 证据；不能断言从未限流，SDK 可能内部恢复。

逻辑在途观测值：Eco、2p、8p、53p 的响应消息都记录过“仍有 4 个请求进行中”；Sky 记录过 5 个；样本记录过 1 个。配置 batch worker 并发分别为 4，样本为 2。这个在途值来自合并遥测，不是完整 HTTP 并发峰值，也不是在途均值。事件开始/结束条数不平衡（例如 8p 为 211/245，而 trace 有 275 calls），不能配对生成假的请求时间线。

批次排队、结果 ready 到 commit、主线程等待按序 future、提交锁等待、provider gate 和冷却等待都缺少完整时间戳。虽然 profiler 某些 queue_wait_s/retry_count 默认填 0，不能解释成真实零等待/零重试。LLM 清洗有部分 queue_wait 观测；翻译批次的零缺乏同等证据。各批次阶段 items 只有耗时、没有逐阶段起止，无法计算阶段区间并集或并行隐藏耗时。

## Tokens 和长短文档对比

运行 trace 的 Tokens 来自提供商响应 usage；state.llm_usage 的 exact_token_calls 全为 0，只能提供字符/4 的角色估算。Eco 两次运行 trace 合计输入 166,389、输出 523,949、缓存 19,328 Tokens，而状态估算输入 145,861、输出 16,984；两者不同不是可以互换的数。usage 输出可能包含模型内部推理计费等部分，但没有 reasoning_tokens 字段，不能确认。失败请求缺失 usage，不能对零 usage 认定零成本。

Sensorium trace 681 calls，状态账本只有 596；Sky 六个 trace 合计 2,311 calls，状态账本 1,790。覆盖范围、角色封装或持久化失败都可能造成差异；没有 per-call ID 不能确定原因或补齐角色账单。这些不一致已经作为数据限制保留，没有强行调平。

最可比的是 Attention 同篇论文的 2p 和 8p：记录配置都关闭理解、清洗和标注，启用审校，使用同一 OpenCode Go/deepseek 模型。8p 的段数为 2p 的 4.06 倍，逻辑调用为 4.04 倍，但端到端仅 2.43 倍；吞吐为 0.331 对 0.198 段/s。2p 有一条 202.053 s 的极长请求，且 TM/复用减少了候选正文，时间也不同，不能把差异全归因于文档长度或并发效率。

53p 启用了理解、清洗、标注；224p 最后配置关闭审校且使用自定义中转站，并经历多次故障。它们适合说明长文档实际总成本，不适合与 Attention 直接做同策略吞吐排名。验证样本 8 段、7 calls、159.118 s：前置术语约 64 s、知识反馈 Σ83.588 s，说明短任务固定成本可以占优；该验证结果不充当业务性能基准。

资源采样中，2p/8p/53p 平均进程 CPU 约 2.6%/10.4%/6.7%，不支持把这些任务的主要耗时归因于 CPU 算力不足。Sky 部分 run 的 RSS 峰值达到 3,380.59 MB，未记录内存压力、swap 或 OOM，不能将其列为已证实内存瓶颈。2p 和验证样本同进程同时间运行，进程资源及部分全局 runtime 写入计数可能包含其他任务，不能精确归因到单一 job。

## 可复现性与验证

`audit.py` 只使用 Python 标准库读取原目录，不执行 Folith、不发送请求；它保存筛选清单、5 个业务任务及样本的精简证据快照，自动计算批次分布、累计阶段工作量、自然历时/已存运行区间并集、上下文比例、retry 事件数和里程碑间隔。生成表见 metrics.md，解释和因果限制见本文件。

复现同一快照：
