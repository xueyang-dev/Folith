# Folith 性能优化路径

依据：[真实任务审计](README.md)、[实测指标](metrics.md)。设计日期：2026-10-08。本文件是实施方案；本次仅新增文档，没有执行付费实验或修改生产代码。

推荐顺序：**补齐最小计时并确认当前基线 → 标注有界并发 → 知识反馈依赖拆分与重叠 → 批次和上下文受控实验**。故障恢复正确性作为前两步的准入条件，验证当前已有机制后，只修复仍能到达的问题。

## 1. 目标与实验边界

主指标是同一输入、同一配置下，从 worker 开始到全部已启用自动步骤完成的墙钟时间。另报“译文及审校完成”“标注完成”“导出完成”三个里程碑；人工审批等待单列。当前没有最终交付耗时基线，实施第一步时补齐。

各阶段保留相同的模型、提示词、审校覆盖、修复规则、知识反馈触发规则、标注范围、术语优先级和交付门禁。并发变化仍可能影响状态可见性，必须验证依赖；不能仅凭“调用同一函数”宣称质量等价。

历史实测用于选择方向，不直接作为新版本 A/B 的对照组。先固定当前代码版本，再在隔离的任务目录中复制相同输入和配置进行比较。TM、知识缓存、翻译缓存从同一份起始快照复制，冷启动与缓存复用分开报告，避免后跑的一组借用前一组缓存。

基准保留三种实际负载：Attention-2p 检查短任务回退，Attention-8p 检查常规翻译吞吐，Sensorium-53p 检查理解、翻译、标注整条链。Sky-224p 的故障和版本跨度过大，作为恢复案例与后续规模验证，不作为第一轮速度对照。验证样本只做快速冒烟。

## 2. 第一批：最小遥测与当前版本基线

实施位置：`folith/trace.py`、`folith/performance.py`、`core.py` 的请求、批次及运行结束边界。扩展现有 trace，不另建遥测系统。

先补四组数据：

1. 请求记录落盘：job/run/batch/role、逻辑请求 ID、请求起止、状态、错误、提供商 usage 及其缺失标志。已保存的逻辑调用数要能由请求记录重算；SDK HTTP 尝试单独关联，不能把外层调用直接称为实际 HTTP 请求。
2. 等待记录：入队、worker 开始、结果 ready、按序提交开始/结束、provider gate/backoff。批次及子阶段保存单调时钟起止，以区间并集计算实际占用。
3. 结束记录：成功、失败和取消均关闭已开始的 span；进程异常结束留下未闭合标记。存储故障下不承诺必然成功写日志，也不能让日志异常覆盖原始错误。
4. 固定口径：container_wall、item_sum、interval_union 分开；无观测填缺失，有明确禁用/跳过记录才填零。增加构建版本及每次续跑的配置快照。

逐请求事件使用现有写入路径的缓冲能力，按现有阶段/运行边界刷新，不给每条开始/结束事件增加 fsync。质量状态的持久化保障继续使用现有机制。TTFT 仅在现有传输能可靠提供时记录，不为取得这个指标改变请求协议。

验收：由请求记录重算调用数、usage 和并发；失败/取消可追溯；重放固定响应时业务结果一致。遥测开销的工程目标为墙钟增量不超过 1%，这是验收目标，不是已测结果。若达不到，先减少事件序列化和锁占用，不牺牲请求关联信息。

同时检查已有 `workflow_errors.py`、`request_control.py`、`workflow_recovery_test.py`：余额不足/无权限不得继续拆批重试，磁盘满不得覆盖最后可读快照，取消后不得新派发付费请求，活跃 worker 不应被重复启动。当前代码已经包含这些保护；测试或当前构建重现失败才开修复项。对已发出的请求与错误传播前的竞争窗口分别计数，不能要求物理上撤回已经发送的请求。

## 3. 第二批：优先并发化自动标注

这是最明确的首个速度改动。Sensorium 的标注耗时 3,188 s，占总耗时 43.13%。`annotate_batch` 的请求只包含本批双语文本和固定提示词；跨段的数量限制、术语覆盖及去重在本地执行。

具体方式：

- 预先计算现有批次及 offset，保持原来的批边界和 prompt。
- 使用小型有界 worker 池发出标注请求，先验证并发 2，通过后再评估 4。复用现有 provider 请求控制和取消上下文；不单独叠加另一套重试。
- worker 返回结果，不直接写共享 state。主线程按原批次顺序合并并保存，最后仍按原顺序执行全局术语覆盖和 `_clean_annotations`。
- 继续使用 `annotation_batches`、`annotations_done_offset` 和现有保存机制。完成进度不能越过未处理批次；失败批次仍被标记并在续跑时重试。限制预取窗口，控制取消后已付费但尚未保存的结果数量。
- 若多任务共享提供商出现等待/429 上升，优先减少标注并发；只有实测证明需要统一在途上限，才在现有请求控制器中增加该能力。

验证首先使用固定响应回放，刻意乱序返回，确认最终 spans、类型、全局数量上限、去重和失败状态与串行结果完全一致；覆盖取消、失败批次续跑和保存失败。随后才做同配置真实 API A/B，检查错误率、限流、Tokens 和人工抽查质量。

首轮工程目标：标注墙钟至少降低 30%，长任务端到端至少降低 10%，请求批数和输入内容不增加。若模型服务延迟或限流抵消收益，停留在较低并发；若状态/结果不等价，退回串行实现。

只作容量参考的理想计算：假设仅标注提速、其余阶段及单请求耗时不变，则 `T新 = 7390.804 - 3188 + 3188 / 标注加速倍数`。

| 假设的标注加速倍数 | 理想标注耗时 | 理想总耗时 | 总耗时下降 |
|---|---|---|---|
| 2 倍 | 26.57 分钟 | 96.61 分钟 | 21.57% |
| 4 倍 | 13.28 分钟 | 83.33 分钟 | 32.35% |

这些不是预测或承诺。并发 4 不等于实际加速 4 倍；长尾、共享额度和写入仍需计入。

## 4. 第三批：移出知识反馈中的可并行远程等待

Sensorium 的知识反馈累计 3,179.449 s，翻译循环仅 3,295.760 s。它位于主提交路径，值得优先于普通本地 CPU/磁盘优化处理。

现有 `knowledge.py` 已将远程 `extract_observations` 与候选项/实体/冲突合并分开，且 `knowledge_cache.py` 已提供相同请求复用。复用这些结构，不再新增缓存层。

但两类依赖必须保留：`accepted_for_knowledge` 依赖实际审校与检查结果；反馈是否触发依赖已有候选项和已知名称。后续翻译提示词又可能读取知识反馈结果。把整个 `observe_batch` 丢进线程池会改变这些行为，不能作为本轮直接改动。

实施分两步：

1. 先用第一批的时序定位“远程抽取等待”“本地合并”“结果 ready 后等待提交”，确认 3,179 s 在当前版本的构成。固定响应回放中记录每批触发决定、抽取输入、知识状态版本及后续实际 prompt。
2. 只对已证明触发决定和合法译文输入均已确定、且不依赖尚未提交状态的批次，提前进行远程抽取；结果仍在原提交顺序中应用。不得为可能会被规则跳过的批次进行额外付费抽取。保留原有上下文可见性边界；对依赖链未解开的批次保持顺序执行。

进入真实 A/B 的条件：固定响应下，调用集合、每批决定、抽取输入、实体和候选项顺序、审校结果以及后续 prompt 全部等价。若无法证明这些条件，结束这条并行化尝试；需要放宽反馈时效或频率的方案另列为质量策略变更，不混入此次实施。

指标是反馈在关键路径上的暴露等待和总翻译时间，不用累计工作量下降冒充加速。暂不承诺百分比，也不把 3,179 s 直接视为可以全部节省；现有翻译 worker 已经与部分反馈重叠。

## 5. 第四批：有数据后再试批大小与上下文成本

这一步会改变请求组合，质量等价不能由结构保证，应作为独立实验，生产默认值在结论形成前保留。

先记录每次实际请求的正文、system、术语、摘要、邻接文本及连续性组件大小，分别标注字符估算和精确 usage。优先查可避免的完全相同计算是否命中现有缓存；不按前缀占比直接删上下文。业务状态中的上下文日志每批只记一次，不能用于估算重试重发总量。

批大小实验只改变一个因素：保留 2,400 字符预算和现有语义边界，先比较段数上限 4 与 8；同时固定并发、模型、质量策略和缓存起点。若段数上限增加仍受字符预算约束，或需要更多拆批/修复，就据此停止。只有第一轮显著有利才测试下一档，不做大规模参数网格。

考察端到端时间、实际请求数、输入/输出/缓存 Tokens、P95、解析与段落对齐失败、修复次数、术语/实体一致性和人工双盲片段复核。任何漏段、错位或门禁绕过直接淘汰；语言质量差异不以简单分数掩盖，应核对具体案例。上下文压缩、减少审校和降低知识反馈频率需单独讨论，不能作为纯性能补丁推广。

## 6. 每一批的决策与交付

| 批次 | 可独立交付的结果 | 继续条件 |
|---|---|---|
| 第一批 | 请求/阶段可重算遥测、当前版本基线、已有恢复保护验证结果 | 能区分实际等待与并发累计值；异常路径可追溯 |
| 第二批 | 标注并发及顺序落盘，乱序/取消/续跑验证，真实 A/B 报告 | 正确性通过且端到端收益可重复 |
| 第三批 | 知识反馈依赖结论；仅在等价条件成立时交付抽取重叠 | 调用与知识可见性保持等价，暴露等待确实降低 |
| 第四批 | 批大小/上下文成本实验结论和具体质量差异 | 收益超过 API 波动且质量证据支持推广 |

每次只改变一个性能因素。先进行一次成对真实试跑；若结果受明显长尾影响或收益接近噪声，再追加反向顺序的成对试跑。短样本不足时不报告稳定的任务级 P95。长文档只对已通过小样本和固定响应验证的候选进行整篇验证，控制实验请求成本。

每个实施改动保持独立、可回退。沿用现有参数和调度结构，不为实验建立常驻功能开关体系。生产推广依据是同版本对照与真实质量检查，而不是历史任务之间的速度差异。

本阶段不安排普通状态写入重构：已测单任务 state_commit 总量不到 1 秒，收益优先级低。文档理解及术语准备也先保留；只有新时序证明它们成为新的关键瓶颈，再分析内部依赖。下一项最合理的实施工作是第一批的最小遥测和基线，随后立即验证标注并发。
