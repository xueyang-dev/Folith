# 0.8.2 验收对账表（快速发布口径）

日期：2026-11-16（2026-11-17 更新）。**发布日期：待定（P2-21 修复合入后）。** 用户 2026-11-17 裁定：P2-21 修好之前不发布。

这张表按 0.8.2 快速发布方案（用户 2026-11-15 裁定）重写：0.8.2 的发布门槛从原计划 §13 的完整验收矩阵收缩为 **9 条**，其余整体移到 0.8.3。

本表取代原来那份 33 条的 §13 草稿。旧草稿的逐条判定不再维护——它回答的是「完整计划做到哪一步」，而 0.8.2 要回答的是「这 9 条门槛过了没有」。已经在 main 上的证据（XLIFF 内核、方言只读、独立校验、界面走查等）在 §3 单独列出，**它们本身不是门槛**，只是救急时可查的记录。

怎么读：

- **通过**：这一条要求的动作做完了，有能点开的记录（Actions run、证据文件、截图），并且记录里的机器/构建/命令能对上。
- **进行中 / 待执行**：动作还没做完，或者做完了但记录还没落盘。
- **未达**：做完了且如实记录了结果——包括没达到目标的那些。**「未达」不是「没测」**，两者在本表里分开写。
- 离屏测试、mock、单元测试**不能**代替冻结包或真窗口。

| **P2-21** | Windows 上打开大任务时**原生崩溃**：CI 的 S3 轮约 **50%/轮**。两种形态：run `43809682882`（s3b）是 `access violation`，faulthandler 标的当前线程是**主线程**、栈顶在 `app.exec()` 的 Qt 原生派发；run `43812245496`（s3）是 `Fatal Python error: Aborted`，当前线程是 worker 线程、栈顶 `Garbage-collecting` | **「崩溃」= 发布阻塞** | **修复已合入，待复核**。两个根因各一个修复：[#443](https://github.com/xueyang-dev/Folith/pull/443)（`78d62025`）采样器不再把被检查线程的帧拖进循环垃圾；[#446](https://github.com/xueyang-dev/Folith/pull/446)（`e5f5941d`）采样器默认不再跨线程取帧（`FOLITH_JANK_OTHER_THREADS=1` 才打开）。判别实验 run `44050865338`：旧默认 **7/20 崩溃**、只采主线程 **0/20 且每轮 exit 0**。**还差一步**：监工在 main 上跑 20 轮复核并通过后才写「已修复」；发布仍等这一步（用户 2026-11-17：P2-21 修好之前不发布） |

这一项**不属于九条门槛里的某一条**，但它落在第 1 条冻结期内的「发布阻塞修复」，也直接影响第 4 条（Windows 冒烟可能整轮崩）与第 9 条（S3 轮次可能崩）。发布前必须看到它的结论：修好，或者停在明确边界并写进已知问题。

**用户裁定（2026-11-15）**：第 7–9 条要求「测完并如实报告」，**不要求达到 70%**。达到写达到，没达到写没达到，不调参凑数。因此第 7 条的「未达」本身**不阻塞发布**；阻塞发布的是第 1–4 条的崩溃、数据损坏、主流程走不通、XLIFF 导出写坏、Windows 冷启动失败或残留进程。
