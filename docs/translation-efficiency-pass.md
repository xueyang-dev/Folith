# Translation runtime efficiency pass — measurement report

This document records an efficiency pass over the **existing** Folith translation
runtime: prompt cost, exact reuse, prompt slimming, batching, concurrency and
review overhead. No new infrastructure was introduced, and no area listed as
protected in the brief was redesigned.

Everything below is measured, not estimated. The harness is
`scripts/translation_efficiency_benchmark.py`; the tables are regenerated by
`scripts/translation_efficiency_report.py`.

## 1. How the numbers were produced

* **Workload**: `benchmark/translation-efficiency/workload.json` — a committed
  fixture extracted verbatim from a real completed job
  (`outputs/6bd045b3a3a7ec60`, *OECD The Space Economy at a Glance 2026*):
  239 segments, min 6 / median 130 / max 278 characters, plus the real document
  profile, synopsis, section digests, entity registry, glossary and the run's
  reference translation.
* **Driver**: the real `core.translate_stage`, unchanged, over the real prompt
  assembly, batching, TM and persistence paths.
* **Provider**: a deterministic local provider that maps each requested source
  segment to its reference translation and never touches the network. Because
  the output is stable, a change that scrambles, drops or reorders work shows up
  as a quality delta instead of hiding inside a latency average.
* **Not measured**: real provider latency and protocol-failure rates under
  larger prompts. The local provider sleeps a fixed amount per request, so
  wall-clock figures are a *projection* under a stated model. Request counts,
  token counts, prompt composition, cache behaviour and quality are exact.

Reproduce:

```bash
python3 scripts/translation_efficiency_benchmark.py \
    --label final --concurrency 1 --latency 0.05 \
    --rerun --resume --partial --out tmp/translation-efficiency
python3 scripts/translation_efficiency_report.py \
    --baseline tmp/translation-efficiency/baseline.json \
    --stages tmp/translation-efficiency/stage-cache.json \
             tmp/translation-efficiency/stage-slim.json \
    --final tmp/translation-efficiency/final.json
```

**Baseline provenance.** The baseline row was captured with this same harness
*before* the changes below. All eight diff hunks in `folith/context.py` belong to
this pass, so the baseline prompt assembly is exactly `git show HEAD:folith/context.py`
with the same `core.py`; the cache contributes nothing to a cold run. The
recorded baseline figures are reproduced in the tables here.

## 3. Changes

### 3.1 VLM provenance gate (Phase 0 closure)

`core._source_quality_gate_enabled` applied the OCR-fragment heuristics to every
`.pdf`, including PDFs whose semantics came from the VLM document-understanding
path. Trusted VLM blocks such as short lowercase headings were quarantined as
"OCR fragments" and withheld from translation pending human source review.

The predicate now reads `extraction_report.semantic_source` and skips the gate
for `vlm` / `mixed`, failing closed for legacy states without provenance. The
disabled report carries `reason: "vlm_semantic_source"` so the decision is
auditable. Regression: `tests/source_quality_test.py`.

Navigation was already covered
(`tests/document_understanding_test.py::test_geometry_failure_never_blocks_semantics_or_page_navigation`,
`::test_persisted_multi_page_spans_merge_split_undo`): segment → persisted source
span → correct PDF page → region highlight when available, page-only fallback
otherwise. No duplicate coverage was added.

### 3.2 Exact translation result cache

`folith/translation_cache.py`, wired through `core.translate_stage`, is separate
from TM on purpose: TM is reviewed linguistic memory scoped by target language;
this is "this exact computation was already paid for".

**Key.** A SHA-256 over the canonical JSON of
`{version, provider, model, temperature, response_format, system prompt, user prompt}`.
Hashing the fully rendered request rather than a hand-maintained field list means
any change that would change the bytes the model sees is a miss *by
construction* — source, glossary, context, style, model, generation settings —
and partial invalidation falls out for free: changing one confirmed term only
rewrites the glossary section of the batches that actually inject it.

**Storage.** One bounded JSON file beside TM and scoped the same way
(`translation_cache_path(project_id)` → `outputs/translation_cache.json` or
`outputs/projects/<uuid>/translation_cache.json`), so it survives UI rerun, job
resume and application restart. Written with the existing process-lock +
re-read + merge + temp-file + atomic-replace shape from `save_tm`, on the state
snapshot cadence and once at stage end. Growth is bounded on two axes — 4096
entries and 8,000,000 retained characters, oldest-first eviction, plus a
200,000-character per-entry rejection — because entry count alone is not a bound
when a document is configured with very large batches. A corrupt or
version-bumped file degrades to empty.

**Safety.** Only a fully parsed, count-matching batch is stored; a failed or
malformed reply is never cached. A hit skips the provider call only — ordering,
TM, review, findings and persistence are untouched, and `from_tm` stays `false`.
Invalidation is covered by `tests/translation_cache_test.py` for changed target
language, changed terminology, changed prompt, changed context, changed model and
changed generation settings, plus disk round-trip, concurrent-writer merge,
bounding and corrupt-file behaviour.

### 3.3 Prompt slimming

Three changes, all removing duplicated information rather than shortening prose:

1. **One whole-document narrative per request.** The per-batch packet no longer
   repeats `document_arc` next to `summary` (measured 62.8% containment; in the
   source job `document_arc` was a raw JSON array whose Python `repr` leaked
   brackets and quotes into the prompt). `document_arc` stays in the persisted
   synopsis for review/UI; it is simply not re-sent 61 times.
2. **Neighbour de-duplication.** A paragraph already shipped as the `原文` of its
   accepted translation is no longer also shipped as a bare previous-source
   bullet. The surviving copy carries strictly more information.
3. **Compact entity hints.** The constant `provenance` / `优先级` boilerplate is
   gone; the section header already states these are advisory and that human
   decisions win. The pair, type, aliases and note remain.

`folith/context.py` now also returns per-section and per-category character
counts from the renderer, which is the accounting surface used above.
Regression: `tests/translation_prompt_slimming_test.py`.

## 4. Audits that ended in "do not change"

### 4.1 Micro-batching

Measured, same workload, same code:

| Config | Batches | Translation input tokens | vs default |
|---|---|---|---|
| 4 × 2400 (default) | 61 | 50,904 | — |
| 6 × 2400 | 41 | 37,303 | −26.7% |
| 8 × 2400 | 31 | 30,392 | −40.3% |
| 8 × 4800 | 31 | 30,392 | −40.3% |
| 4 × 1200 | 61 | 50,904 | 0.0% |

The character budget never binds: `4×1200` and `8×4800` produce byte-identical
results to their 2400 counterparts. The segment cap is the only binding
constraint, and it is what carries the measured token waste.

**This lever was already tested against a real provider in this repository and
rejected.** `scripts/batch_tuning_report.py` / `docs/translation-throughput.md`
record: median latency 10.6 s (4×2400) → 38.8 s (6×4800) → 50.0 s (8×6400), with
protocol failures 1/4 → 3/4 → 2/4. Production job states at 4×2400 show 0, 0 and
0 protocol failures over 61, 61 and 63 batches. Raising the count cap is exactly
the change that evidence rejects, and the deterministic harness here cannot
validate protocol failure or latency growth. **Default batching was left at
4 × 2400**; the token table above is recorded so the trade-off is not re-derived
blindly.

### 4.2 Concurrency

| Workers | Wall time | Speedup | Batches seeing an empty accepted-target window |
|---|---|---|---|
| 1 | 7.60 s | 1.00× | 1 / 61 |
| 2 | 3.81 s | 1.99× | 4 / 61 |
| 3 | 3.89 s | 1.95× | 6 / 61 |
| 4 | 3.91 s | 1.95× | 8 / 61 |

(A second sweep on an otherwise idle machine gave 1.91× / 1.92× / 2.04×; the
plateau at roughly 2× is the stable finding, the exact figure is load-sensitive.)

Target digests, segment counts and source order are identical at every level. The
only difference is continuity: with N workers the first N batches run before any
target is committed, so fewer batches see an accepted-target window. The shipped
Qt adapter already runs at 4 (`folith/qt/adapter.py:82`); the library default of
1 in `core.DEFAULT_TRANSLATION_CONCURRENCY` is the serial, continuity-exact path
used by tests. The existing `ThreadPoolExecutor` model is sufficient (2.04× at 4
workers) and was not replaced; `review_overlap`/`section_scheduler` were left
alone.

The review prompt also carries the whole-document summary and full synopsis —
including the duplicated `document_arc` — bounded only by the packet's 12 000 /
16 000 char limits, which are far larger than the slimming budget the generation
prompt now uses. Per the brief this pass only *quantifies* review; the review
architecture is unchanged.

## 6. Quality evidence

Every run above reports identical: 239/239 segments, 0 empty targets, preserved
source order and target digest, reference agreement 1.000, the same
deterministic findings, and 0 terminology violations. `tests/translation_cache_test.py`
and `tests/translation_prompt_slimming_test.py` additionally assert that a cache
hit never impersonates TM and that the slimmed packet still renders every
mandatory section within its budget.

**Limit of this evidence.** The deterministic provider cannot judge translation
quality. Prompt slimming removes content the audit measured as duplicated, but
the residual quality effect of dropping the second whole-document narrative is
not measurable in this harness. It is a low-risk change — the surviving summary
covers 62.8% of it, and the batch still receives the unit summary, unit
translation rules, entity hints, glossary, style rules, document profile and
local neighbour context — but a human or live-model spot check on a
representative chapter remains the correct next validation step.

## 7. Removed / avoided complexity

* No scheduler, no queue, no external database, no vector store, no semantic
  cache, no tokenizer dependency (the existing `ceil(chars/4)` estimator in
  `folith/usage.py` is reused consistently).
* No change to batching and no change to concurrency, both after measurement.
* No review redesign and no selective-review gating.
* No terminology change: filtering was already correct (0–1 terms per batch).
* Not taken: the per-batch metadata log (`core.context_metadata`) re-renders the
  whole context packet a second time purely to record `prompt_chars`. Removing
  that duplicate render would save well under 1% of stage CPU and would change a
  persisted log field, so it was left alone.

## 8. Remaining bottlenecks

| Rank | Cost centre | Measured |
|---|---|---|
| 1 | **Review** (when enabled) | 69.2% of input tokens, 3.0× the per-call prompt of translation, +49% wall time, +50% requests |
| 2 | **Translation prompt context** | 81% of each generation prompt is still repeated context; whole-document summary (138 tok/req) and unit rules (135 tok/req) are the two largest single sections |
| 3 | **Knowledge feedback (auxiliary)** | 61 requests for 239 segments, 17,102 input tokens, equal to 50% of the request count and 25% of input tokens in the cold run — one model call per batch |
| 4 | **Source payload** | 8,458 tokens, irreducible |
| Not in this workload | Document understanding / VLM | one-time per document, not on the per-batch hot path |
| Not measured here | Export / delivery | outside the translation runtime |

## 9. Recommended next optimization

**Make independent review risk-selective instead of mandatory per batch.** It is
the single largest measured cost centre (69.2% of input tokens, 3.0× the
per-call prompt of translation), it is already gated by a deterministic signal —
`check_translation_batch` blocking/actionable findings, TM provenance,
locked-term conflicts, entity drift — and the repository already ships a
risk-targeted review path (`_targeted_final_review_ids`) for the whole-book pass.
The same discipline applied per batch (review every batch that carries any
deterministic finding or risky segment; skip the clean remainder, or shrink the
review packet's 12 000/16 000-char context budgets toward the generation
packet's) would remove the majority of the review token spend without touching
the review evidence model. It is deliberately **not** attempted in this pass
because it changes a quality contract, and the deterministic harness cannot
prove the absence of a quality regression.
