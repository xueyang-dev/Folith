## 权威边界与事务崩溃语义（Correctness & Crash Guarantees）

### 1. 架构权威边界划分
- `state.json`：唯一权威完整任务快照。
- `state_journal.jsonl`：仅作为最近一次快照之后的翻译热路径持久化增量，严格从属于 `state.json`。
- `events.jsonl`：工作流审计与证据序列，禁止充当日志真值。
- `runtime_events.jsonl`：运行期遥测。

### 2. 六类严苛崩溃用例（`tests/state_journal_test.py` 全绿）
- **Case 1（追加前崩溃）**：记录未落盘，恢复时该批次不存在，续跑时按断点重算该批次，无脏数据。
- **Case 2（追加后、快照前崩溃）**：快照落后于日志。`core.load_job_state()` 触发 `journal.replay()`，直接在内存还原最新 pairs 与 review 统计，**0 次模型调用**即可完全恢复。
- **Case 3（快照完成后、日志清理前崩溃）**：快照携带最新 `journal_cursor`，重复 replay 时直接短路跳过，**绝不产生重复 pairs**。
- **Case 4（Compaction 中途崩溃）**：原子更替遵循 `write temp -> replace state.json -> rotate journal -> unlink`，任何时刻盘上均存在至少一条完整且一致的真值链路。
- **Case 5（TM 晋升 pending 崩溃）**：TM 为派生缓存，重放时依据已确认的 pairs 幂等重导，无条目重复污染。
- **Case 6（人工介入编辑优先）**：用户编辑后保存会立即触发日志 compaction 并推进版本号，旧的模型生成记录绝不会覆盖人工编辑。

### 3. 数据不变量验证
100 / 1000 / 5000 段的译文真值指纹在 Baseline、Phase A、Phase B 间**逐字符完全一致**：
- 100 段：`c746b5b98a9c7748`

- 5000 段：`a6383421880a8c41`
- `reviewed_count == segment_count`，`source_order_preserved == True`，`resume_batches_remaining == 0`。

## 优化去留审计（Final Decision Matrix）

| 优化项 | 结论 | 归因依据 |
| --- | --- | --- |
| **紧凑 JSON 序列化** | **KEEP** | 序列化加速 3.8–4.0×，体积减少约 20%，stdlib 原生无依赖，语义与编码完全等价 |
| **作业目录缓存 (`_ensure_job_dir`)** | **KEEP** | 消除每批冗余 `mkdir`，耗时从 2.37ms 降至 0.01ms |
| **交付快照条件门控** | **KEEP** | 移出非 final 阶段的无谓遍历，消除随快照数增长的 O(N) 外部开销 |
| **翻译记忆节奏匹配与紧凑化** | **KEEP** | `save_tm` 耗时下降 90%，写入量减少 88%，等价性测试全绿 |
| **状态日志机制 (`state_journal.jsonl`)** | **KEEP** | 彻底粉碎 O(n²) 写入放大，5000 段全量快照从 1250 次降至 3 次，写放大降至 2.33× |
| **强类型 Mutation + Cursor 幂等重放** | **KEEP** | 保证重放纯 IO 零模型调用，通过 6 类崩溃一致性验证 |
| **日志驱动的自适应快照预算 (`journal_bytes + fraction`)** | **KEEP** | 解耦快照频次与文档长度，使超长文档写放大平稳受控 |
| **Dirty-domain 状态粒度分离** | **REVERT** | 审计证实扫描瓶颈在 Journal 实施后已被频次削减完全掩盖，强行引入易破坏状态权威契约 |
| **增量 summary.json 构建** | **REVERT** | `build_job_summary` 本身仅 0.006ms，瓶颈在写入已随快照降频解决，无需增量构造复杂度 |

## 当前最新 Top 3 瓶颈与下一轮建议

### 当前系统瓶颈重排（5000 段实测）
1. **模型调用与网络交互框架开销**（翻译生成 + 修复 + 审校，假 LLM 下累计耗时 ~43s，占整轮 ~75%）：在真实 Provider 下时延占绝对主导。
2. **上下文组装与知识检索 (`_setup`)**：TM 精确扫描、术语匹配与上下文打包（累计 ~8s，占整轮 ~14%）。
3. **剩余持久化系统调用**：主要是每批 `state_journal.jsonl` 的 `fsync`（累计 1250 次追加约 0.3s，占整轮 ~2%）。

### 下一轮最值得做的一项（Next Best Optimization）
**审校重叠流水线（Reviewer Overlap Pipeline）**
- **依据**：第二轮与当前实测均确认，翻译主循环串行等待审校专家返回占用了约 49.5% 的纯等待时延。
- **设计要点**：
  1. 翻译主线程并发严格保持为 1（不破坏有序性与上下文连贯性）；
  2. Translator 完成生成与确定性 QA 后发布不可变快照 $S_n$，立刻启动 $B_{n+1}$ 的生成；
  3. Reviewer 消费不可变快照，异步给出审校意见，由单线程按 batch index 升序提交；
  4. 预期在真实 Provider 环境下将端到端翻译耗时缩短约 35–45%。
