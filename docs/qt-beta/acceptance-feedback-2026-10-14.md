## 1. 点进度条弹出运行记录浮窗

**原话**：任务进度详情的显示按钮可以放到进度条上，用户点进度条就出现一个小浮窗，从进度条扩大弹出；点 ❌ 或其他地方，浮窗消失。

### 1.1 现状（已核对代码）

- 顶栏进度条：`folith/qt/views.py:1653`，普通 `QProgressBar`，**高 6px、宽 160px**，只在运行时显示，不可点击。
- 运行记录现在是工作台里的一整页（`ActivityPanel`，`folith/qt/activity_panel.py`），入口藏在步骤条右侧的「更多」下拉菜单里（`folith/qt/stagebar.py:300`），与「原页 / 检查与修复 / 任务详情」并列。要看一眼进度，得切走当前页面，看完再切回来。
- 仓库里还没有任何浮窗（`Qt.Popup`）组件，需要新做一个，放进 `components.py` 以便复用。

### 1.2 方案

1. **可点击的进度区**：把进度条包进一个约 28px 高的透明按钮区域（6px 的条本身几乎点不中），悬停时显示手型光标和浅色底，提示文字「查看运行记录」。右侧加一个百分比数字（例如 `91%`），顺便解决现在只有条、没有数字的问题。支持键盘：Tab 聚焦，回车 / 空格打开。
2. **浮窗 `RunActivityPopover`**：
   - 用 `Qt.Popup` 窗口：点外面、按 Esc 都会自动关闭，这是系统行为，不用自己写全局点击监听；右上角放 ✕。
   - 位置：锚定在进度条下方、右边对齐窗口，约 440×380；靠近屏幕边缘时自动往里收。
   - 内容从上到下：
     - 标题行：当前阶段 + 进度（如「翻译 · 2909 / 3201 段 · 91%」）+ ✕。
     - 最近约 50 条运行记录（复用 `ActivityPanel` 的行数据和配色），默认停在最新；用户往上翻时不自动跳回底部。
     - 底部两个按钮：「在 Finder 中显示完整日志」「打开完整运行记录」（跳到现有整页）。
   - 打开期间实时追加新记录。必须沿用现有的签名比对，内容没变就不重绘，否则每秒的状态刷新会让浮窗闪烁或被重建。这个坑 `stagebar.py:302` 已经踩过一次。
3. **「从进度条扩大弹出」的动画**：约 150ms，几何尺寸从进度条的矩形插值到浮窗最终矩形，同时透明度 0→1；关闭时反向，约 100ms。系统开启「减少动态效果」时直接出现，不做动画。
   - 说明：Qt 的独立窗口做不了真正的缩放变换，只能用几何插值近似。内容在动画期间先隐藏，到位后再显示，避免文字被压扁。

### 1.3 影响与风险

- 涉及文件：`views.py`（进度区）、新组件 `components.py`（浮窗）、`activity_panel.py`（行数据抽成共用函数）、5 个 locale 文件（新文案）、`style.py`（浮窗与进度区的 QSS）。
- 测试：新增 `tests/qt_run_popover_test.py`，覆盖点击打开、Esc / 点外面 / ✕ 关闭、运行中追加记录不重建、键盘打开、任务结束后进度区隐藏且浮窗自动关闭。
- 风险 1：`Qt.Popup` 打开时会抓走鼠标和键盘。需要确认浮窗开着时，「暂停 / 取消」按钮第一次点击是先关浮窗还是直接生效（系统默认是先关浮窗）。
- 风险 2：已知的 QTBUG-149612（macOS 辅助功能扫描导致崩溃）与表格类辅助节点有关。浮窗里用的是 `QListWidget`，理论上不受影响，但需要人工验收确认。

## 2. 新建任务 → 准备 → 开始翻译，切换卡顿

**原话**：开始翻译前，新建任务、准备、开始翻译这一整个流程，每个界面切换的时候过渡会卡顿，不丝滑，没有做到原生的质感。

### 2.1 实测（隔离数据目录，真实窗口，8ms 心跳计时器测主线程停顿）

测量脚本：[`measure_new_task_flow.py`](acceptance-feedback-2026-10-14-tools/measure_new_task_flow.py)（用法：`venv/bin/python -I <脚本> <文档路径>`）：导入 → 自动打开任务 → 停在「准备」→ 点开始，统计主线程超过 50ms 的停顿。60fps 下一帧是 16ms，停顿超过约 100ms 人就能明显感到「卡了一下」。

| 文档                                       | 导入并打开           | 停在准备页（5 秒） | 点开始后 20 秒内                     |
| ---------------------------------------- | --------------- | ---------- | ------------------------------ |
| 验收样本.docx（小）                             | 1 次，最长 **89ms** | 0          | 2 次，最长 **113ms**               |
| The Midnight Library.pdf（308 页 / 3201 段） | 最长 **4.1 秒**    | 74ms       | 4 次，最长 **9.5 秒**，合计 **19.6 秒** |

小文档是「每一步都顿一下」；大文档则是窗口直接冻住好几秒。两者原因相同，只是规模不同。

### 2.2 根因（按耗时排序，来自 cProfile）

1. **打开任务时，所有东西都在主线程同步算完才显示**（`window.py:871 open_job`，代码注释里已经承认「可达 1–2 秒」）：
   - 交付预检 `adapter.delivery_preview` 1.44s；其中 `entity_registry.consistency_findings` 0.65s；
   - 原页 PDF 首页渲染 `pdf_panel._render → render_pdf_page_image` 0.75s；
   - **重复计算**：`open_job` 先 `_load_setup` + `workbench.load`（里面已经 `apply` 一次），紧接着又 `refresh_workbench(force=True)`，把 `load_state`、`_load_setup`、`segment_rows`、`delivery_snapshots`、`apply` 全部再做一遍。
2. **每次刷新都销毁再重建控件**：例如 `review_panel.apply` 每次都调用 `filter_control.set_options`（`style.py:1264`），删掉并重新创建全部分段按钮。新控件要套用整份全局 QSS 重新 polish，profile 里 2 次调用就花了 1.67s。审校队列 `_rebuild_list` 同样是 `clear()` 再全部重建。
3. **后台流水线和界面抢 GIL**：翻译 worker 是同一进程里的线程。点开始后主线程自己的 Python 耗时约 5s，但实测冻结合计 19.6s，多出来的部分是主线程在等 worker 释放 GIL（大 PDF 抽取、长时间持有状态锁写文件等）。这一条要用 `py-spy dump` 在冻结瞬间抓栈才能定位到具体代码，**目前是推断，尚未证实**。
4. **观感层面**（与耗时无关，但直接影响「原生质感」）：
   - 导入、开始翻译都会弹出模态的「正在导入…」「正在启动翻译任务…」小框（`prompts.BusyDialog`），一闪而过，比卡顿本身更像不是原生应用；
   - 页面切换（任务库 ⇄ 工作台、准备面板 → 段落网格）是硬切，没有过渡；
   - 准备面板换成段落网格时，整块正文区重排，布局会跳一下。

### 2.3 方案（分三步，每步都能独立验收）

**第一步：先消除冻结（收益最大，风险低）**

- `open_job` 改成两段：先用已有的 state 和段落行立即切到工作台（只渲染首屏需要的内容）；交付预检、原页渲染、一致性检查交给现有的 `self.runner` 在后台算，算完再填进去。需要先确认这些 adapter 函数是只读、可以跨线程调用的。
- 去掉 `open_job` 末尾那次重复的 `refresh_workbench(force=True)`，或者让 `load` 之后的这次刷新命中缓存、直接跳过。
- 原页 PDF 改为切到「原页」时才渲染，不在打开任务时渲染。

**第二步：控件改为原地更新，不再重建**

- `SegmentedControl.set_options`：选项的 key 没变时只改按钮文字（计数），不删按钮。
- 审校队列、运行记录等列表：按稳定 id 做增量更新，不再 `clear()` 后全部重建。
- 每处都保留现有的签名比对，内容没变就什么都不做。

**第三步：观感**

- 用行内状态代替导入、开始时的模态 BusyDialog：按钮变成「正在启动…」并禁用，加一个小转圈（第 12 条 A 去掉底部状态栏之后，这里不再同步写状态栏）。真正耗时很长的操作（例如超过 3 秒的导入）再显示进度。
- ~~页面切换加 120–150ms 的淡入~~ → **按决策 D1 执行**（从卡片展开约 300ms、准备 → 网格约 250ms 等，见 D1 细则）；准备面板 → 段落网格先固定正文区高度，避免布局跳动。系统开启「减少动态效果」时只保留淡入淡出。
- 先做 `py-spy` 抓栈，确认 GIL 争用的来源，再决定是缩短 worker 持锁的时间、在热点循环里主动让出 GIL，还是长期把流水线挪到子进程。子进程是大改动，本轮**不建议**做。

### 2.4 验收标准

用同一个脚本复测：小文档整个流程没有超过 50ms 的停顿；大文档打开任务时主线程停顿 ≤ 100ms（内容可以分批出现）；点开始后不再出现超过 200ms 的冻结（第三步的 GIL 问题解决之前，先以「不超过 1 秒」为阶段性目标）。

## 3. 「更多」里的页面改成浮窗

**原话**：更多里面的这几个功能（原页 / 检查与修复 / 运行记录 / 任务详情）都做成小浮窗，而不是像现在这样直接把主屏幕完全占住，这样是不是会好一点。

> ⚠️ **本条已由决策 D2 / D3 取代**：原页改为「工具栏按钮 → 工作台左侧展开」，检查与修复改为「进度条旁的状态图标」，「更多」只剩任务详情、改成 ⓘ 浮窗。下面的表格和 3.3 的两个问题保留作背景，**不再执行**；只剩 Q1（检查与修复打开后的形态）待定。

### 3.1 我的判断：方向对，但四个页面的用法不同，不适合都用同一种浮窗

| 页面    | 用户在里面做什么                       | 推荐形态                         | 理由                               |
| ----- | ------------------------------ | ---------------------------- | -------------------------------- |
| 运行记录  | 看一眼进度和最近的步骤                    | **轻浮窗**（就是第 1 条那个）           | 只读、看完就走；点外面关闭正合适                 |
| 任务详情  | 看文档画像、设置、来源信息，偶尔点「编辑画像」        | **轻浮窗**                      | 以只读为主，内容不长                       |
| 检查与修复 | 逐条处理问题：点一条 → 跳到对应段 → 改译文 → 下一条 | **右侧抽屉**（不遮挡段落网格，点外面**不**关闭） | 轻浮窗一点外面就消失，而用户恰恰要去点网格里的段落，会反复关掉  |
| 原页    | 对照原 PDF 看版面                    | **右侧抽屉，或者可拖动的独立小窗**          | 需要足够的面积，并且要和段落网格同时可见；轻浮窗太小，也会被点掉 |

两种形态：

- **轻浮窗**：`Qt.Popup`，锚定在触发按钮下方，点外面 / Esc / ✕ 关闭。和第 1 条共用一个 `Popover` 组件。
- **右侧抽屉**：从右侧滑入，占据现在检查器的位置，宽约 420px，可以拖动调整宽度。段落网格仍然可见、可以操作；点抽屉右上角的 ✕ 或再点一次入口才关闭。打开抽屉时，原来的段落检查器暂时让位，关闭后恢复。

这样主屏始终是段落网格，四个页面都不再整页替换它。「更多」菜单本身保留，改成打开对应的浮窗或抽屉。

### 3.2 影响

- 和第 1 条共用浮窗组件，和第 2 条的「原页按需渲染」也是同一处改动，适合一起做。
- 改动集中在 `views.py`（页面现在都放在 `self.tabs` 里，要从标签页里拆出来）和 `stagebar.py`（「更多」菜单的行为）。另外需要新增一个 `Drawer` 组件。

## 7. 应用图标改成纯白背景

**原话**：顺便把下版本图标的背景换成纯白色，例如 Chrome。

3. 补上 1024px（`icon_512x512@2x.png`）这一帧。
4. 生成图存一份到 `folith/resources/brand/folith-app-icon-white.png`，纳入版本控制，方便设计复核；`.icns` 仍然只是构建产物。

同一时刻最多显示一个气泡。用户点「不再显示提示」后，全部关闭。

### 9.3 实现要点

- 「已完成引导」和「哪些提示已看过」存在 QSettings 里（`onboarding/completed_version`、`onboarding/tips_seen`），不放数据目录。这样，两台机器共用一个数据目录时，各自都会看到引导；数据目录被导入导出时，这些标记也不会跟着走。
- **老用户升级**：已经有任务、或者已经配置过模型的用户，不显示完整的欢迎流程，只显示一次「0.5 有哪些新变化」（Qt 客户端、原页面板、检查与修复图标等），一页就结束。
- 脚本化运行（`FOLITH_QT_NONINTERACTIVE=1`）和测试里一律不显示，避免挡住探针和用例。
- 欢迎窗口和情境提示都要支持键盘操作（Tab、回车、Esc 跳过）和 VoiceOver 的朗读文本。
- 依赖关系：第 2 步依赖第 8 条的设置重构，情境提示依赖第 1 条的浮窗组件和 D2 / D3 的新入口。所以它应该**排在这些之后**做，否则引导里指向的控件马上又会变。

### 9.4 验收

- 用全新的 QSettings 和空数据目录启动：出现欢迎窗口，四步都能走完，也都能跳过；关闭后重启不再出现；「帮助 → 新手指南…」可以重新打开。
- 用示例文档能完整走完 准备 → 翻译 → 审校 → 交付（用 d0 stub 模型做自动化测试）。
- 已有任务的数据目录：只出现「新变化」一页。
- 每个情境提示只出现一次，同一时刻只出现一个；点「不再显示提示」后全部关闭。

### 9.5 需要你决定

1. **要不要附带示例文档？** 推荐要：新用户最大的门槛是「手边没有合适的文件试一下」。内容可以由你提供（例如你自己写的一段双语介绍），也可以用公有领域的作品（例如古腾堡计划里的短篇开头）。
2. **情境提示要不要做？** 推荐做，但可以先只做欢迎窗口，情境提示放下一轮。
3. **老用户升级时，要不要显示「新变化」那一页？**

## 10. 打开暂停过的任务时，客户端卡死

**原话**：刚才我点开一个中途暂停的工作，大概卡了四五秒，整个客户端卡死。需要优化，加入动画和进度条或者怎么样，就是不要卡死。

### 10.1 实测（The Midnight Library 任务的副本，放在隔离目录里，原数据未改动）

测量脚本：[`measure_open_existing_task.py`](acceptance-feedback-2026-10-14-tools/measure_open_existing_task.py)（用法：`venv/bin/python -I <脚本> <任务目录>`；脚本会先把任务目录复制到临时目录，不会改动原数据）。

任务规模：3708 段，943 条审校记录，`state.json` 有 23.1 MB。

| 测量 | 结果 |
|---|---|
| 打开任务（`open_job`），不开 profiler | 主线程**冻结 10.5 秒** |
| 打开之后，每次状态变化触发的刷新 | 每次冻结约 **2 秒** |

你那边看到的是 4–5 秒，大概是因为任务规模不同、机器负载不同。根因是一样的，而且**任务越大、审校记录越多，卡得越久**，会随着翻译进度持续变差。

### 10.2 根因：一个平方级的扫描（不是界面的问题，是数据层的算法问题）

cProfile 的结果非常集中：

- `translation_evidence.translation_review_readiness`（`folith/translation_evidence.py:296`）对**每一段**（3708 段）都调用一次 `current_review_event`；
- `current_review_event`（同文件第 57 行）每次都从头到尾**倒序扫描全部 943 条审校记录**，并且对每一条都重新构建一遍段号列表（`_review_segment_ids`）；
- 结果是 `_review_segment_ids` 在一次打开里被调用了 **3600 万次**，约占总耗时的 87%；
- 没找到当前审校的段，还要再扫一遍全部记录，去找历史记录（第 336 行）；
- `workbench_view._historical_event`（`workbench_view.py:149`）也是同样的写法：每个队列项都倒序扫描一遍全部记录；
- 更糟的是，同一次打开里 `translation_review_readiness` 被调用了 **6 次**：交付预检、审校队列、段落详情各算一遍，还有第 2 条里说的重复刷新。

**这个函数在翻译流水线里也会被调用**（`core.py:7723`）。所以它很可能也是第 2 条里「点开始后界面冻结 19.6 秒」的元凶之一：worker 线程在跑这个平方级循环时，一直占着 GIL，界面线程抢不到。

### 10.3 方案（按收益排序）

1. **把平方级的扫描改成一次建索引**（核心修复，改动很小）：
   - 新增一个 `_review_index(state)`：倒序遍历一次 `review_evidence`，建两张表：「段号 → 最新的、未过期的当前审校记录」「段号 → 是否有历史记录」。判断条件和现在逐条判断的逻辑完全一致：跳过 `stale_segment_ids` 里的段，跳过 `freshness_status == "stale"` 的记录，跳过之后继续看更早的记录。
   - `translation_review_readiness`、`current_review_event`、`workbench_view._historical_event` 都改成查这个索引。复杂度从「段数 × 记录数」降到「所有记录里段号的总数」。
   - 用 state 的签名做缓存键，同一个 state 只建一次索引，供同一轮刷新里的 6 次调用共用。
   - **等价性测试**：用真实任务的副本和随机构造的 state，逐段对比新旧实现的结果必须完全一致，再加一个规模测试：5000 段、1000 条记录时，计算时间低于 50ms。
   - 预期效果：仅这一条，打开这个任务的时间就能从 10.5 秒降到 1 秒左右。
2. **打开任务时不再阻塞主线程**（就是第 2 条第一步，这里一并落实）：
   - 点击任务后，先立即切到工作台，显示标题和一个骨架屏（灰色占位行，带缓慢的光泽动画），这样用户马上就能看到「正在打开」；
   - 读取 `state.json`（23 MB 的 JSON 解析加深拷贝，profile 里约 1.5 秒）、构建段落行、审校队列、交付预检这些都放到后台线程；完成后按「段落网格 → 检查器 → 交付预检」的顺序依次填进去，每一块出现时做一次淡入；
   - 后台计算期间，如果用户已经点了别的任务或者返回了任务库，就丢弃这次的结果，不再回填。
3. **去掉重复计算**：`open_job` 末尾那次 `refresh_workbench(force=True)` 和 `load` 里的 `apply` 是重复的，合并成一次；交付预检只在打开「交付」时、或者任务到达终态时才算。
4. **大 state 的读取**：`load_job_state_cached` 每次都会对 23 MB 的 state 做一次隔离拷贝（`_isolated_copy`）。打开一次调用了 8 次，合计约 1.5 秒。界面层是只读的，可以改成共享一份不可变的视图，或者至少在同一轮刷新里只拷贝一次。

### 10.4 验收

- 用同一个副本复测：点击任务后 100ms 内出现工作台骨架；主线程在任何时刻的冻结都不超过 100ms；完整内容在 1.5 秒内填满。
- 运行中每次状态刷新，主线程冻结不超过 50ms。
- 等价性测试通过，新旧实现的审校就绪结果逐段一致。
- 第 2 条的「点开始后冻结」用同一个脚本复测，看这一条修完之后还剩多少，以此判断 GIL 争用里还有没有别的来源。

## 11. 运行状态和进度条合在一起，进度条用颜色表示状态

**原话**：左上角这个灰色的字显示当前的运行状态，能不能把这个运行状态和进度条放在一起？而且进度条可以变颜色，来展示状态是否正常：是正在工作，还是出故障卡住了。

### 11.1 现状

- 左上角标题下面是一个状态胶囊「正在运行」，旁边是灰色的小字「正在等待模型响应」（运行视图里的 `detail`）；进度条在右边，和「暂停 / 取消」按钮放在一起。两者隔着整个顶栏，用户要左右来回看。
- 进度条只有一种颜色。重试、长时间没有进展、出错，看上去都和正常运行完全一样。
- 运行视图其实已经区分了这些状态：`running`、`translation_retry`（正在重试，比如 CI 里见过的 HTTP 500 第 2/3 次尝试）、`stalled`、`failed`、`paused`、`interrupted`、`completed`。只是界面没有用上。

### 11.2 方案：顶栏右侧做成一个「运行状态组」

```
[ 进度条 ███████░░░ 91% ]   [检查与修复图标]   [暂停] [取消]
  翻译 · 2905 / 3201 段 · 正在等待模型响应
```

- 进度条（第 6 条的原生感 `ProgressTrack`）下方紧贴一行小字：「阶段 · 进度 · 当前在做什么」。左上角只保留文件名和状态胶囊，那行灰字挪到这里。
- 整个组是一个点击区域，点开就是第 1 条的运行记录浮窗。
- **颜色与状态**（颜色从来不是唯一的提示：每种状态都同时有文字，必要时加图标，方便色弱用户和 VoiceOver）：

| 状态 | 进度条 | 下方文字示例 |
|---|---|---|
| 正常工作 | 系统强调色（蓝） | 翻译 · 2905 / 3201 段 |
| 等待模型响应 | 蓝色，加一道缓慢移动的光带（第 6 条） | … · 正在等待模型响应 · 12 秒 |
| 正在重试 / 响应变慢 | **琥珀色**，光带变慢 | … · 模型暂时不可用，正在重试（第 2/3 次） |
| 卡住（长时间没有进展，`stalled`） | **琥珀色**，停止光带，文字后面加 ⚠ | … · 已有 3 分钟没有进展，可以暂停后重试 |
| 出错（`failed`） | **红色**，停在出错时的进度 | 翻译失败：服务商暂时不可用（HTTP 500） · 点击查看 |
| 已暂停 / 已中断 | **灰色** | 已暂停 · 2905 / 3201 段 |
| 完成 | **绿色**，约 2 秒后收起为「已完成 · 12 分钟」标签（第 1 条的 Q3） | 已完成 |

- 颜色切换时用约 300ms 的颜色过渡，不要硬切；切到琥珀色或红色时，配合第 D3 条的图标做一次轻微的提醒动画。系统开启「减少动态效果」时，只切颜色，不做动画。
- **「卡住」的判定**：运行时数据里已经有 `last_progress_at`、`model_wait_started_at`。以「距离上次进展超过 N 秒」为准，N 先取 120 秒（大模型单批响应的正常上限），之后可以根据实际日志调整。核心层已经有 `stalled` 状态的地方直接用核心层的判定，界面层不重复发明。

### 11.3 和其他条目的关系

这一条把第 1 条（浮窗入口）、第 6 条（进度条样式）、第 D3 条（检查与修复图标）、第 5 条第 5 点（步骤条里不要塞「批次」）合成了一个完整的「运行状态组」。**建议这四条放在一起做**，避免顶栏来回改动好几次。

## 12. 设计原则：相关信息集中在一处

**原话**：参考我这种想法，相关的信息和状态就把它们整合在一起，实现信息的合理集中，用户不用到处找信息来源。类似可以这样做的地方还有吗？

### 12.1 原则（写进设计规范，以后新功能都按这个检查）

1. **一个对象，一个家**：任务、段落、术语、模型连接、交付，每一类信息都有一个「主位置」，所有相关的状态、数字、操作都在那里能看到，其他地方只放指向它的入口。
2. **状态挨着它描述的东西**：状态文字、颜色、数量，放在被描述的那个控件旁边，而不是放在窗口另一头的状态栏或者一个弹窗里。
3. **同一个概念，处处同一种表达**：例如「有问题」这个状态，在任务卡片、顶栏图标、段落行、筛选项里，都用同一个颜色、同一个图标、同一个叫法。
4. **摘要在前，细节一点即开**：主位置只放最重要的一两个数字，点开浮窗或抽屉才看到完整内容（第 1、11 条就是这个模式）。


### 12.2 现状排查：信息分散在多处的地方

| # | 信息 | 现在分散在哪里 | 用户的困扰 |
|---|---|---|---|
| A | **出错和提示消息** | 窗口底部的状态栏（`window.py` 里 97 处 `showMessage` / `_notice`）、55 处模态错误弹窗（`_failure`）、运行记录、页面里的横幅 | 状态栏的字很小，几秒后就消失，很容易错过；模态弹窗又会打断操作；而且底部状态栏和顶栏显示的是同一件事（截图里两边都写着「正在运行 · 正在等待模型响应」） |
| B | **模型连接状态** | 侧栏底部的「已配置 自定义中转站 / deep…」、设置里四块连接配置、任务库的黄色横幅、准备面板里的连接问题提示 | 「已配置」不等于「能用」；要知道审校模型、视觉模型是不是也通，得打开设置一个个点「测试连接」 |
| C | **术语** | 顶栏「术语」按钮、检查器里的术语区、侧栏「术语与翻译记忆」页、检查与修复里的术语问题、筛选里的「术语问题」 | 同一条术语的定义、在文中出现的位置、被违反的地方，分在三四个页面里 |
| D | **一段的完整状态** | 段落网格（只有段号、原文、译文）、检查器（审校状态、需要注意、术语、前后文）、检查与修复（这段的问题）、筛选菜单（人工修改、翻译记忆、批注） | 在网格里扫一眼，看不出哪一段被人工改过、用了翻译记忆、有批注、有术语问题，只能逐段点开检查器，或者逐个试筛选条件 |
| E | **任务的概况** | 任务卡片（状态、进度线）、准备面板（交付格式、风格）、任务详情页（文档画像、用量）、设置里的任务默认值 | 想知道「这个任务用的是哪个模型、目标语言、要交付哪些格式、花了多少 token」，要在准备、任务详情、设置三处来回找；而任务一旦开始，准备面板就看不到了 |
| F | **交付** | 步骤条的「交付」、交付页、准备面板里的交付格式、设置里的默认交付格式、Finder 里的输出目录 | 交付前不知道还差什么（审校没完成？阻断问题？），要进了交付页才知道 |
| G | **任务库里看任务进度** | 卡片只有状态和一条进度线；问题数、是否卡住、是否出错，都要打开任务才知道；而打开一个大任务要卡 10 秒（第 10 条） | 不进任务就无法判断哪个任务需要处理 |
| H | **版本、数据位置与支持信息** | 「关于」通知框（版本）、「诊断信息」对话框（数据目录、日志、运行事实）、即将新增的「存储」页（第 8 条）、发行说明（卸载说明） | 同一类支持信息有三四个入口 |
| I | **字数** | 底栏左边（整份）、底栏右边（当前段）、「字数统计…」对话框 | 已经在第 4 条里合并 |

### 12.3 整合方案

- **A. 统一的「通知」层**（参考 macOS 的通知和 Mail 的活动视图）：
  - 和某个任务有关的状态与错误，一律进第 11 条的运行状态组：颜色、文字，点开就是运行记录浮窗，里面能看到完整的错误原因和「重试」按钮；
  - 和任务无关的一次性结果（「已导入 3 个文档」「已复制」），改成窗口顶部居中的一个轻提示（toast），停留 3 秒后自动淡出，鼠标悬停时不消失；
  - 只有**需要用户做决定**的情况（删除确认、冲突、无法继续）才保留模态弹窗；纯粹的告知类错误不再弹窗；
  - 底部状态栏去掉，它和顶栏重复，而且字太小；
  - 规模：中。55 处 `_failure` 要逐个判断归到哪一类，这是主要工作量。
- **B. 侧栏底部做成「连接状态」芯片**：显示总体状态（● 全部正常 / ● 视觉模型未测试 / ● 翻译模型连接失败）。点开是一个浮窗，逐项列出翻译、审校、视觉三个连接的状态和上次测试的时间，每项都能直接「测试」，并跳到设置里对应的那一页。准备面板和任务库横幅里的连接提示都改成链接到这里。规模：小–中。
- **C. 「术语」做成一个对象主页**：顶栏「术语」按钮上显示数字（锁定 N · 待确认 M · 冲突 K）。点开是一个浮窗或抽屉，列出本任务的术语，每条术语都显示：首选译名、出现在哪些段（可以点击跳转）、违反了几次、来自全局 / 项目 / 本任务。检查与修复里的术语问题，点进来也落到这里。侧栏的「术语与翻译记忆」页保留为跨项目的管理页。规模：中。
- **D. 段落行上的状态标记**：在段落网格的段号旁边加一列小图标（✎ 人工修改、⟲ 来自翻译记忆、Aa 有术语、⚠ 有问题、💬 有批注）。图标和筛选菜单的条目一一对应：点图标就等于套用这个筛选。这样扫一眼就能看到全局，筛选菜单也就不再是唯一的查看方式。规模：中。需要注意大文档下的绘制性能，要用 delegate 自绘，不能每行放几个控件。
- **E. 任务概况卡片**：任务开始之后，把准备阶段的选择（模型、目标语言、风格、交付格式）、文档画像、用量（调用次数、token、耗时、翻译记忆省下的部分）合成一张「任务概况」，就是 D3 里说的 ⓘ 任务详情浮窗，而不是让这些信息在准备面板消失之后就看不到了。规模：小（内容都已经有，主要是重新排版）。
- **F. 交付就绪度**：步骤条上的「交付」直接显示是否就绪（✓ 可以交付 / 还差 12 段待审校 / 2 个阻断问题）。悬停时显示清单，点「还差 12 段」直接跳到第一段。依赖第 10 条：交付预检要先算得够快，才能实时显示。规模：小–中。
- **G. 任务库卡片显示运行状态和问题**：卡片上的进度线使用第 11 条的颜色语义（蓝 / 琥珀 / 红 / 灰 / 绿），旁边显示问题数图标（与 D3 一致）。「有错误」「卡住了」在任务库里就能一眼看出来，不需要打开任务。数据来自 `summary.json`，不用加载完整的 state，所以不会变慢。规模：小。
- **H. 支持信息合并到设置的「关于」与「存储」两页**：版本、构建、GitHub 链接、报告问题都在「关于」；数据位置、占用、清理、导出、卸载说明都在「存储」。「诊断信息」保留为「关于」页里的一个按钮，用来生成支持包。「关于 Folith」菜单直接打开设置的「关于」页。规模：小（和第 8 条一起做）。

### 12.4 需要你决定

上面 A–H 你想做哪几处？我的推荐：
- **这轮做**：A（通知层，影响最广）、B（连接状态）、E（任务概况）、G（任务库卡片）、H（随第 8 条一起做）。这几处主要是重组已有的信息，风险小，效果明显。

## 13. 快速 / 标准 / 精细：工作流差异、耗时与 token

**原话**：看一下准备界面的三个模式（快速、标准、细致）在工作流上到底有什么区别，速度差多少，token 消耗呢？我担心分级不明确的问题。

（界面上第三档显示为「精细」，内部的键是 `学术增强`，定义在 `folith/application/task_setup.py:59`。）

### 13.1 预设本来的设计

| 开关 | 快速 | 标准 | 精细 |
|---|---|---|---|
| 建立文档画像（全文理解） | ✗ | ✓ | ✓ |
| 自动识别术语 | ✗ | ✓ | ✓ |
| 使用翻译记忆 | ✓ | ✓ | ✓ |
| 译后独立审校 | ✗ | ✗ | ✓ |
| 严格术语治理（锁定已确认术语） | ✗ | ✗ | ✓ |
| 分句方式 / 并发 / 批次 | 按句 / 4 / 稳妥 | 同左 | 同左 |

设计本身是一个合理的递进。**但实测发现，这张表在实际运行时并不成立。**

### 13.2 发现两个 bug：模式开关没有真正生效（已用脚本证实，不调用模型）

**Bug 1：「审校」「自动识别术语」「翻译记忆」三个开关，跟的是全局设置，而不是任务选的模式。**
- 「准备」面板保存「快速」之后，任务状态里写的是对的：`enable_review=False`、`auto_term=False`。
- 但真正交给流水线的配置（`adapter.pipeline_kwargs`）是 `enable_review=True`、`auto_term=True`。
- 原因：`folith/application/settings.py:208` 的 `_TASK_FIELDS` 里，`auto_term`、`enable_review`、`use_tm` 这三个字段**没有配置 `state_keys`**，解析时根本不读任务状态；而 `start_job` 传入的显式层是全局的 `EngineConfig`（`adapter.py:524`，也就是设置里「任务默认值」的那几个勾选）。于是全局设置总是赢。
- 后果：选「快速」也照样跑全量审校。你的 The Midnight Library 任务就是例子：任务标的是「标准」，却跑了 1007 次审校调用。
- 对照：`enable_understanding` 配置了 `state_keys`，所以「建立文档画像」是唯一按模式生效的开关。

**Bug 2：「精细」的严格术语治理永远不生效。**
- `apply_task_setup` 把它写成 `strict_terminology_governance=True`，但解析器读的是 `quality_mode` 这个键（`settings.py`：`state_keys=("quality_mode",)`）。键名对不上，读到的是 False；流水线启动时又用这个 False 覆盖了 `state["quality_mode"]`（`core.py:10901`）。
- 后果：「精细」承诺的「锁定已确认术语」从来没有执行过。

**两个 bug 叠加，现在三档真正的区别只剩下「建立文档画像」这一项。** 审校开不开、术语识不识别，完全取决于设置里的全局默认值，和你在准备面板选了哪个模式无关。这就是「分级不明确」最直接的来源。

### 13.3 修好之后，三档的真实差距（实测）

脚本：[`compare_strategy_presets.py`](acceptance-feedback-2026-10-14-tools/compare_strategy_presets.py)（用法：`venv/bin/python -I <脚本> 快速|标准|学术增强`，每次一个模式、一个全新数据目录）；原始结果在 [`compare_strategy_presets.results.jsonl`](acceptance-feedback-2026-10-14-tools/compare_strategy_presets.results.jsonl)。13.2 的两个 bug 用 [`probe_preset_resolution.py`](acceptance-feedback-2026-10-14-tools/probe_preset_resolution.py) 复现（不调用模型）。本机开着系统代理时，需要先设置 `NO_PROXY=127.0.0.1,localhost`（见第 14 条）。

方法：仓库里的 239 段测试文档（OECD 报告，约 3.2 万字符英文），每个模式各用一个**全新的数据目录**（排除翻译记忆和缓存的跨轮复用），流水线、提示词都是真实的，只是用本地 stub 代替模型。让全局设置和模式保持一致，这样每档的开关确实生效（相当于 bug 修好之后的效果）。token 用流水线账本里「字符数 ÷ 4」的估算值。

| | 快速 | 标准 | 精细 |
|---|---|---|---|
| 模型调用次数 | 141 | 149（+6%） | 210（+49%） |
| 输入 token | 约 5.2 万 | 约 6.6 万（+27%） | 约 13.5 万（+160%） |
| 其中：翻译 | 4.1 万 | 4.4 万 | 4.4 万 |
| 其中：辅助（画像、知识反馈等） | 1.1 万 | 2.2 万 | 2.2 万 |
| 其中：独立审校 | 0 | 0 | **6.9 万（占精细总量的 51%）** |
| 估计耗时\* | 约 5 分钟 | 约 5–6 分钟 | 约 7–8 分钟 |

\* stub 是瞬时响应的，所以耗时是用你 Midnight Library 任务里真实测到的平均单次延迟（翻译 8.2 秒/次、审校 7.7 秒/次、辅助 8.4 秒/次）加上并发 4 推算的，**只能看相对差距**。

**换算到你那本书的规模**（3708 段，按同样的比例；你那次实际跑的是「标准 + 全量审校」）：实测输入 174 万 token，其中审校 122 万、占 70%，模型累计耗时 4.5 小时，其中审校 2.2 小时。如果真的按「标准」跑（不审校），输入大约 52 万 token，模型耗时大约减半。

几点说明：
- stub 的术语抽取返回为空，所以「标准 / 精细」里术语注入带来的额外 token 没有体现出来，真实情况下会再高一些。
- 输出 token 是 stub 生成的假内容，不可信，表里只列输入。
- 「快速」也有 49 次辅助调用（约 1.1 万 token）：这是每批一次的「知识反馈」，即使关掉了自动识别术语也照样执行，和「快速」的定位不符。

### 13.4 结论：分级问题有两层

1. **开关不生效**（13.2 的两个 bug）：这是正确性问题，必须修。用户选了「快速」却按全量审校计费，选了「精细」却没有锁定术语。
2. **修好之后梯度也不均匀**：
   - 快速 → 标准：调用次数只多 6%，token 多 27%，时间几乎一样。用户感受不到「快」的好处；而「标准」多出来的画像和术语识别，是质量上很划算的投入，几乎不费时间。
   - 标准 → 精细：token 翻一倍以上，这一跳几乎全部来自独立审校。
   - 也就是说，真正的成本分水岭只有一个：**开不开独立审校**。现在三个档位的名字（快速 / 标准 / 精细）暗示的是三个均匀的台阶，实际上是「两档几乎一样 + 一档贵一倍」。

### 13.5 方案

**A. 先修 bug（必须做，规模小）**
- `settings.py` 的 `_TASK_FIELDS`：给 `auto_term`、`enable_review`、`use_tm` 加上 `state_keys`，让任务保存的选择优先于全局默认值；`strict_terminology_governance` 的 `state_keys` 改为同时认 `strict_terminology_governance` 和 `quality_mode` 两个键，并在 `apply_task_setup` 里两个都写，兼容旧任务。
- 新增测试：对每个预设，「准备面板保存后的 `pipeline_kwargs`」必须和预设的取值完全一致，并且分别在全局默认值全开、全关两种情况下各测一遍。
- 已有任务：它们保存的值本来就对，修好之后，下次继续运行时就会按任务自己的设置执行。但像你这本「标准 + 已经审校过」的书，继续运行时会停止审校剩下的段落。需要在发行说明里写清楚，或者对已经开始审校的任务保持原样。**这一点需要你决定**（13.6 第 1 问）。
- 「准备」面板和任务头部：配置和预设不一致时，模式名直接显示「标准 · 已自定义」，而不是只显示「标准」。

**B. 让三档的差距清晰、诚实（推荐）**

| | 快速 | 标准（默认） | 精细 |
|---|---|---|---|
| 定位 | 先看个大概 / 内部阅读 | 正式翻译 | 出版、学术、对外交付 |
| 做什么 | 只翻译，加确定性检查（术语、格式、数字） | + 文档画像 + 术语识别 + 翻译记忆 | + 逐段独立审校 + 锁定已确认术语 |
| 批次 / 并发 | 「均衡」批次，并发 6，关闭每批知识反馈 | 稳妥批次，并发 4 | 同标准 |
| 相对成本（以标准为 1） | 约 0.6 | 1 | 约 2 |

- 快速：改成更大的批次和更高的并发，再关掉每批一次的知识反馈。这样它才真的「快」，token 和时间预计都能比标准少三到四成。上线前要用同一个脚本复测，并检查批次返回项数不符的比例没有明显上升（大批次的已知风险）。
- **在每张模式卡片上显示「针对这份文档」的预估**：约 N 次调用 · 约 X 万 token · 约 Y 分钟。按段落数、字符数和上面实测的比例计算，并标注「估算」。这样用户选的时候就知道差多少，不用跑完一次才知道。
- 卡片文案直接写出最关键的差别：精细 =「每一段都由第二个模型独立审校一遍，费用约为标准的 2 倍」。
- 准备面板的「高级」区里，保留单独开关审校的选项，给想要「标准 + 审校」的人用；这种组合直接显示为「自定义」，并显示预估。

### 13.6 需要你决定

1. **已经开始的旧任务**（例如那本标为「标准」、实际在审校的书）：修好 bug 之后，继续运行时是按任务保存的模式执行（停止审校），还是保持它到目前为止的实际行为（继续审校）？推荐**保持实际行为**：只对修复之后新建的任务严格按模式执行，旧任务在准备面板里标注「本任务开启了审校（自定义）」。实现上，迁移时在已经开始的任务的 state 里写入它实际生效过的值（`enable_review` 取 `translation_core_review_required`，`auto_term` / `use_tm` 取当时全局配置的取值），并记下 `strategy_migrated_at`，使「实际行为」变成任务自己显式保存的选择，不再依赖全局设置。
2. 同意 13.5 B 的三档重新定位吗？特别是「快速」改用更大的批次、并发 6、关闭知识反馈这一点。
3. 模式卡片上的预估（调用次数、token、时间）要不要做？推荐做，这是解决「分级不明确」最直接的办法。

## 14. 开着系统代理时，连接本机模型返回 502（测试时发现）

### 14.1 现象与根因

- 跑第 13 条的实测时，所有发往本机 stub（`127.0.0.1`）的请求都返回 502。
- 本机开着系统代理：`scutil --proxy` 显示 HTTP/HTTPS 代理是 `127.0.0.1:7890`，应该是 Clash 一类的工具。Python 的 `urllib.request.proxy_bypass("127.0.0.1")` 返回 True，说明系统的例外列表本来是包含本机地址的；但模型客户端使用的 HTTP 库仍然把 `127.0.0.1` 的请求发给了代理，代理转发失败，就返回了 502。
- 设置 `NO_PROXY=127.0.0.1,localhost` 之后，请求立刻正常了。
- **影响真实用户**：开着 Clash 的同时，使用本机模型（Ollama、LM Studio）或本机中转站（`http://127.0.0.1:…/v1`）的人，会一直看到「服务商暂时不可用（502）」，而且很难想到是代理造成的。中国大陆用户开 Clash 很常见，所以这个组合并不少见。

### 14.2 方案

- 构建模型客户端时，如果 `base_url` 的主机是 `localhost`、`127.0.0.0/8`、`::1` 或局域网地址，就显式绕过代理（在 httpx 客户端上为这个地址关闭代理，或者把它加进 `no_proxy`）；其他地址继续沿用系统代理，因为不少用户正是靠代理才能访问 OpenAI、Gemini 这类服务。
- 「测试连接」失败、返回 502 或 407，并且检测到系统代理开着时，在错误信息里加一句提示：「检测到系统代理 127.0.0.1:7890；如果模型服务在本机，请把它加入代理的例外列表。」
- 测试：模拟系统代理开启的情况，确认本机地址不走代理、外部地址照常走代理。
- 规模小，改动集中在建立 LLM 客户端的那一处。

### D1 细则：过渡动画怎么做才符合 Apple 的理念

> 📌 已用真实源码和真实窗口做过专项审计：[motion-audit-2026-10-14.md](motion-audit-2026-10-14.md)。结论**以审计报告为准**，下表作为方向参考。审计的要点：
> - 仓库里目前没有任何动画代码、动效 token，也没有读取减少动画的设置；
> - 段落切换的速度没问题（大约一帧），真正的问题是目标行每次瞬移 62px、检查器高度每次跳 70–140px；
> - 验证切片是「段落切换（行高插值加滚动锚定）+ 审校侧栏」；检查器内容、正文、悬停按下、列表项**不加动画**；
> - 新增一个约 80 行的 `folith/qt/motion.py`：时长和缓动 token、`reduced()`（Qt 6.11 读不到系统设置，用 ctypes 调用 NSWorkspace）、按 key 中断的规则，以及快速连点时跳过动画；
> - 前提是先修好第 15、16 条和第 10 条，否则动画会冻在半路。

依据的是 Apple HIG 的 Motion 原则：动画要有目的（交代「东西从哪来、到哪去」），简短，不打断操作，可以被打断，并且尊重「减少动态效果」设置。落到这几处切换上：

| 切换 | 做法 |
|---|---|
| 任务库 → 工作台（打开任务） | ⚠️ 动效审计的最小方案是「侧栏宽度过渡 + 内容区 8px 位移与淡入，300ms」；下面的「从卡片展开」（共享元素）风险更高，放到验证切片通过之后再评估。原方案：**从卡片展开**：被点击的任务卡片作为共享元素，放大过渡到工作台的标题区，其余内容淡入。约 300ms，曲线接近弹簧（快速起步、柔和收尾，不回弹）。这是 Photos / Finder 快速查看那种「东西从哪来」的连续感。 |
| 工作台 → 任务库（返回） | 反向：工作台收回到原卡片的位置，约 250ms。 |
| 准备面板 → 段落网格（点开始翻译） | 准备面板淡出并轻微上移 8px，段落网格从下方 8px 淡入。正文区高度在过渡期间保持不变，避免布局跳动。约 250ms。 |
| 导入 / 开始时的等待 | 不再弹出模态小框；按钮原地变成「正在启动…」并显示系统样式的小转圈。 |
| 原页面板（D2）展开 / 收起 | 面板宽度从 0 展开到目标宽度，中间工作台同步收缩，两者用同一条曲线，约 280ms。 |
| 浮窗（第 1 条、任务详情） | 从触发点（进度条、按钮）放大弹出，约 200ms；关闭约 150ms。 |


通用规则：
- 曲线统一使用一套弹簧近似参数（Qt 的 `QEasingCurve.OutCubic` 起步，必要时自定义贝塞尔曲线），时长 200–300ms，不超过 350ms；
- 动画期间允许继续操作，新的操作会中断旧动画，并从当前位置继续，不会卡住等动画播完；
- 系统开启「减少动态效果」时，位移和尺寸类动画**直接到达终态**（以动效审计 3.2、4 为准；滚动锚定这类不属于动画的稳定措施保留）；开启「减少透明度」时不使用半透明叠层；
- **前提是先消除第 2 条的主线程冻结**：主线程卡顿时，再好的动画也会掉帧。所以第 2 条按「消除冻结 → 原地更新 → 动画」的顺序做，不能颠倒。

### D2 细则：原页左侧展开面板

- 入口：在工作台工具栏（搜索框那一行）加一个显眼的「原页」按钮，带图标，是切换按钮，展开时为选中态。只有 PDF 来源的任务才显示。快捷键 ⌘⌥P。
- 展开后：左侧面板默认占工作台宽度的约 40%，可以拖动分隔条调整，宽度会被记住；段落网格和右侧检查器整体收缩。窗口太窄（例如小于 1200px）时，自动收起右侧检查器，给原页和网格让位。
- 面板内容（对照 Streamlit 版）：
  - 顶部工具条：上一页 / 下一页、页码输入、缩放（适合宽度 / 适合页面 / 100% / 150%）、「定位当前段」、✕ 收起；
  - 主体：大尺寸页面渲染，**高亮当前选中段**的行框；
  - 在网格里选中段落时，原页自动翻到对应的页并高亮；该来源没有行框时，如实显示「只能定位到页，无法按坐标高亮」。
- 性能：只在展开时渲染（和第 2 条的「原页按需渲染」是同一处改动）。翻页、缩放在后台线程渲染，渲染完成前先显示上一张图的缩放版本，不卡主线程。
- 复用现有的 `pdf_panel.py`（已有缩放、定位），把它从标签页里拆出来，放进可动画的分隔面板。

### D3 细则：检查与修复状态图标

- 位置：进度条右侧，一个 28px 的圆形图标按钮（盾牌加对勾的图标）。任务结束、进度条隐藏后，图标仍然保留。
- 颜色与状态：
  - 灰色：没有问题，或还没有审校结果；
  - **黄色**：有需要注意但不阻断交付的问题，右上角显示数量；
  - **红色**：有阻断交付的问题（例如锁定术语违规、格式标记丢失），显示数量；
  - 颜色变化时，图标做一次轻微的「点头」缩放动画（约 200ms），提醒但不打扰；减少动态效果时不做。
- 点击后：打开检查与修复的内容。这一层的形态还剩一个小问题要定（见下面的待定 Q1）。
- 第 1a 条（数字挂在「更多」上的误导）随之解决：问题数只出现在这个图标上。
- 「更多」菜单：原页、检查与修复、运行记录都有了独立入口，菜单里只剩「任务详情」。所以把「更多」换成一个 ⓘ 图标按钮，点开就是任务详情浮窗。如果以后还要往里加别的页面，再恢复成菜单。
