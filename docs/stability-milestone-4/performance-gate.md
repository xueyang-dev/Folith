# 长文档性能门禁（#77）

2026-10-22。取代 `tests/red_team_acceptance_test.py::test_long_document_simulation_and_performance`
里的绝对墙钟阈值。

结论先写在前面：**pytest 里不再保留任何计时判定**，但保留一条确定性的结构判据——
「整份任务状态被加载的次数必须是常数」。定量性能由
`scripts/benchmark_long_document.py` 在空机器上按平台对比基线负责。下面是为什么
只能这样分工。

## 起点：绝对阈值度量的是 runner

原判据是绝对秒数：

```python
limit = 30 if os.name == "posix" else 120
assert q["elapsed_s"] < limit and ql["elapsed_s"] < limit
```

| 观察 | 值 |
| --- | --- |
| macOS arm64，`origin/main` `cfe2f4f` | 70.66 s / 76.73 s |
| 同一测试文件在 CI 上的总耗时 | 47 s（`#67` 基线） → 72–98 s（`#68`） |
| 判据 | 30 s |

同一份代码在不同 runner 上给出相反结论。抬高阈值或加重试都不解决——前者让门禁
失去意义，后者把它变成概率问题。

## 尝试一：同机标定的每段成本比（否决）

```
R = t(2 000 段) / (10 × t(200 段))
```

先跑一份形状相同、规模为十分之一的标定文档，紧接着跑被测文档，同机同进程。
如果 R 只反映代码，它就该与平台无关。事实不是：

| 平台 | 同代码（本分支）的 R（quick） | 2 000 段 / 标定 |
| --- | --- | --- |
| Windows 11 x64，AMD64 Family 25 Model 97，24 逻辑核 | **1.44** | 33.84 s / 2.36 s |
| GitHub Actions `ubuntu-latest`，Python 3.11 | **3.20** | 20.92 s / 0.65 s |

差一倍以上。原因很具体：这条流程**每一批都要把整份 `state.json` 重写一遍**
（2 000 段时约 3.2 MB），所以每段成本本来就随文档长度上升；而"写一个字节"相对
"其余每批固定工作"的占比在两个平台上完全不同（NTFS 与 ext4/tmpfs、本地盘与 CI
临时盘）。**R 于是在 Linux 上暴露超线性、在 Windows 上被固定开销抹平**——任何
单一阈值都会在一侧误报、在另一侧失灵，和原来的绝对阈值是同一个毛病换了量纲。

同一个 R 在 Windows 上跨运行也不稳：同一提交、同一模式测到 1.05 与 1.40。

## 尝试二：两点仿射外推（否决）

用 200 段与 400 段两次测量拟合 `t(n) = a + b·n`，再外推 2 000 段的预算，可以把
固定开销 `a` 扣掉。实测同样不稳：

| 模式 | 外推预算 | 实际 | 实际 / 预算 |
| --- | --- | --- | --- |
| quick | 20.92 s | 33.99 s | 1.624 |
| quality | 27.08 s | 35.35 s | 1.306 |

两种模式差 24%——外推把小文档测量的噪声放大了（`t(2 000) ≈ 9·t(400) − 8·t(200)`，
系数越大越吵）。

## 尝试三：墙钟比值抓不住历史缺陷（负结果）

按 #77 报告里的缺陷形状注入——每次保存都重读并重解析整份快照——实测（quick）：

| 场景 | 2 000 段 | 标定 200 段 | R | half_scale |
| --- | --- | --- | --- | --- |
| 基线 | 33.99–35.01 s | 2.5–2.7 s | 1.32–1.39 | 1.25 |
| 注入（126 525 行重解析） | 43.66 s | 2.50 s | 1.746 | — |
| 注入（157 900 行重解析） | 44.78 s | 2.43 s | 1.84 | 1.441 |

信号是 +20%，而同一主机同一判据的跨运行噪声就是 ±20%。**没有任何墙钟阈值能同时
做到"基线不误报"和"抓住这个量级的注入"**：降到 1.65 能让注入失败，但会把 `main`
的 1.58 放在 4% 余量上，等于把噪声变成随机失败。

## 采用：结构判据 + 粗筛兜底

计时判定全部取消。`tests/red_team_acceptance_test.py` 保留固定规模（2 000 段）、
两种模式下的全部内容断言，并新增一条**与机器、平台、Python 版本无关**的结构断言：

```
load_job_state 调用次数 ≤ 16
```

计数来自 `folith.storage.job_repository` 的签名缓存统计：每次
`load_job_state` 都会记一次缓存命中或未命中，两者相加就是整份快照被加载了几次。
之所以不只用 `disk_reads`（未命中次数）：缓存命中也要整份深拷贝，同样随文档长度
变贵，"每批多加载一次"无论是命中还是未命中都是 O(n²)。运行前
`invalidate_cache()` + `reset_cache_stats()`，使数字只反映这一次运行。

| 场景 | quick | quality |
| --- | --- | --- |
| `main`（clean，Windows，pytest） | **0** | **3** |
| `#68` `367f4b2`（clean，Windows，独立脚本） | **0** | **3** |
| 注入「每次保存都重新加载整份快照」 | **216**（末模式） | — |

注入那一行来自完整的 pytest 运行：墙钟从 68.33 s 涨到 143.86 s（+111%），
`save_job_state` 被调用 422 次、其中 422 次都触发了一次整份快照加载。**失败点
精确落在新的结构断言上**（`tests/red_team_acceptance_test.py:1044`），不是落在
内容断言上——这一点很重要，它说明门禁是因为性能形状而红，不是因为别的原因。

`_HANG_GUARD_S = 1800` 只兜"真的卡死"。耗时仍然打印，供基准对照，但不参与判定。

`scripts/benchmark_long_document.py` 是定量门禁：固定负载、多次取中位数，输出

```
half_scale = t(2 000) / (2 × t(1 000))   # 边际成本，平台内部可比
```

基线按平台各记一份，跨平台不可比。用法见脚本 docstring。

这样分工的理由：墙钟只在一个平台、一台机器、同一负载下才有意义。把它放进每个 PR
都跑的门禁，得到的是随机结论；把它放进"人决定何时跑"的基准，得到的是可比较的数字。
而"整份快照被加载了几次"这件事在任何机器上都是同一个答案，所以它能进每次 PR 都跑的门禁。

## 验收（#77 的三条要求）

在 Windows 11 x64、Python 3.11.16、同一份代码上，通过 `pytest.main` 跑真实用例
（与 CI 同一条入口，不是自己另写的 harness）：

| #77 要求 | 做法 | 结果 |
| --- | --- | --- |
| 机器被拖慢时仍给出有意义的结论，不因负载而失败 | 12 个满载子进程占住 24 核的一半 | **通过**。墙钟 68.33 s → 114.48 s（+67%），旧判据的 30 s 绝对阈值必挂；加载次数仍为 0 / 3 |
| 注入回归时用例必须失败 | 每次保存后追加一次 `core.load_job_state` | **失败，且失败点就是结构断言**。加载次数 216 > 16，墙钟 +111% |
| 三个 Python 版本连续两轮全绿 | Linux 3.10 / 3.11 / 3.12 + Windows | 由 CI 负责，无法在一台 Windows 主机上复现，未在本地声称 |

### 关于本地 harness 的一条如实记录

最早一版验证脚本是在普通 Python 进程里**直接调用**测试函数的，同一条用例在那种
上下文里会挂在内容断言 `reviewed == 2000` 上，而在 pytest 下同一份代码是通过的。
原因没有查清（`save_job_state_atomic` 末尾的 `invalidate_cache` 使注入的强制重载
必然未命中，进而重放 journal 并重跑审校真相核对，是最可疑的方向，但未证实）。
**没有去追这个 harness 问题**：跑失败的不是交付物，交付物是 pytest 里的判据，
所以 harness 改成用 `pytest.main` 跑同一条入口，与 CI 一致。记录在此以免后人
在同一处浪费时间。

### 负载验证

12 个满载子进程占住 24 核的一半，再跑同一条用例：

| 场景 | 墙钟 | 2 000 段 quick | R（quick / quality） | 结果 |

| 空闲 | 76 s | 33.84 s | 1.44 / 1.56 | 通过 |

旧判据下 52.85 s 必然失败（posix 30 s）。这也是当初要换判据的直接动机。
新判据下这条场景仍然通过，且通过的原因与负载无关（结构计数不随负载变化）。

## 门禁分工

| 问题类型 | 判据 | 在哪 |
| --- | --- | --- |
| 重复加载整份快照、体积平方增长 | 计数断言（≤ 16） | 本用例 |
| 存储 / journal 层的读写次数与字节 | 计数断言 | `tests/job_storage_test.py` 等 |
| 绝对性能、跨修订对比 | 中位数 + `half_scale` | `scripts/benchmark_long_document.py` |
| 行为正确性（2 000 段、注入、冲突、审校、交付） | 内容断言 | 本用例 |
| 真的卡死 | 1 800 s 兜底 | 本用例 |

## 这条门禁不覆盖什么

- **绕过 `load_job_state` 直接读 `state.json`**：判据数的是加载调用，不是文件读取。
  直接 `path.read_text()` 读快照的回归要靠 code review 与基准脚本发现。模块 docstring
  已声明 `load_job_state` 是唯一访问入口，所以这属于"明知故犯"一类。
- **回归幅度 < 30% 的墙钟差异**：低于墙钟在共享机器上的分辨力。`#77` 报告里
  "`#68` 让长文流程慢 15–50%"这一条，本机实测 `main` 33.84 s / 42.39 s 与 `#68`
  36.04–43.91 s 完全重叠，落在噪声带内，**不能据此声明任何百分比**。该修复的证据是
  `#68` 的存储回归用例，不是墙钟。
- **均匀变慢**：所有批次同比例变慢时结构计数与 `half_scale` 都不变。相对判据在原理上
  无法区分"代码慢一倍"和"机器慢一倍"。
- **更小批次数之类的人工参数**：批次数是内容断言的一部分（500 批），改它会先在内容
  断言上失败，不会悄悄变成性能问题。
- **UI 响应**：这是管线门禁，不含 Qt 工作台。相关工作见 #44 / #54。
