# 阿拉伯语文本互译与排版验收

本文保留修复前的测试记录。后续实现和验证结果见 [阿拉伯语与任意语言互译及 RTL 修复](arabic-rtl-fixes-2026-10-01.md)。

测试日期：2026-10-01。覆盖中文、英语、俄语与现代标准阿拉伯语的六个双向组合，每个方向 8 个样本，共 48 组。当前结论：文字读取、传递、保存和编辑可用，但工作台及导出排版尚不能作为完整的阿拉伯语 RTL 支持验收通过。

本轮只新增测试样本、验收脚本和证据，没有修改产品实现。任务状态在临时目录中生成，没有调用真实模型、读取凭据或使用已有任务。样本译文是待双语人员复核的参考草稿，不能作为翻译质量金标准。

## 已确认问题

### 工作台缺少原文和译文独立的 RTL 设置

相关实现：`folith/ui/workspace/cat_grid.py` 的 `render_translation_segment_row`，原文 HTML 未设置 `dir`，译文使用普通 `st.text_area`。

英→阿的 8 个译文编辑器实际 `direction=ltr`、`text-align=start`；阿→英的 8 个阿拉伯语原文实际 `direction=ltr`、`text-align=left`。短句字符能够显示和连写，但句末标点位于不合适的位置，长句从左侧换行，中英阿混排更明显。

验收应要求：阿拉伯语所在列使用 RTL、从右侧起排；另一列保持其语言方向。应用的中文导航和整张双语表不需要整体翻转。“右缩进”应进一步区分右对齐、书写方向和首行缩进；只有右对齐不能解决混排顺序。

证据：`workspace-en-to-ar.png`、`workspace-ar-to-en.png`、`browser-results.json`。

### Word 单语及双语导出没有阿拉伯语方向

相关实现：`core.py` 中 `translations_to_word`、`pairs_to_word`、`_apply_doc_fonts`、`_apply_run_fonts`。

六个方向的两类输出都未设置段落 RTL 或右对齐。英→阿实际渲染中，阿拉伯语的换行末行落在左侧，句号位于右侧，数字与英文缩写的视觉顺序不稳定；`OpenAI API: مهلة الطلب 30 ثانية (انظر القسم 2).` 的括号混排也暴露了段落方向缺失。

验收应要求：阿拉伯语段落、双语表中的阿拉伯语单元格按 RTL 排版，并逐项检查括号、数字、URL、占位符和标注后的 run。两列内容顺序维持“原文／译文”。

证据：`word-render/page-1.png`、`word-translation-render/page-1.png` 和 `audit-results.json`。本机 LibreOffice 的中文标题、表头部分缺字属于另一个待核实的字体环境问题，本轮不将其归因于阿拉伯语支持。

### EPUB 有语言标记但没有 RTL 方向

相关实现：`folith/epub.py` 的 `_xhtml` 和 `build_translation_epub`。`lang="ar"` 不会自动设置 CSS 的书写方向。导出的 XHTML 未设置 `dir`，样式表也没有 `direction` 设置；Chromium 实测阿拉伯语正文为 LTR。

验收应要求阿拉伯语正文 RTL，并在真实 EPUB 阅读器中检查章节导航、段落、图注及混排。是否需要向左翻页属于阅读器与阅读习惯的独立验收项，不能仅凭本次浏览器预览判定。

证据：`epub-browser.png`、`epub-browser-results.json`。

### PDF 对英文开头的阿拉伯语段落采用 LTR

相关实现：`core.py` 的 `translations_to_pdf`。当前采用 `dir="auto"`，按首个强方向字符判断段落方向。纯阿拉伯语样本可以正确连写并在右边缘起排；以 `OpenAI API` 开头的阿拉伯语样本却在左边缘起排，与其他阿拉伯语段落不一致。

验收应要求目标语言明确为阿拉伯语时，这类段落仍使用 RTL，同时保持英文缩写、URL 和数字内部顺序正常。当前导出函数只接受 pairs，未接收目标语言；实现修复时需要明确传入语言或采用适当的方向判定规则。

证据：`en-to-ar-pdf-page-1.png`。

## 已记录的能力边界

阿拉伯语样本 `متى يبدأ الاجتماع؟ من المسؤول عن تقديم التقرير؟` 在 sentence 模式仍为一个单元；当前句末字符集合未包含 `؟`。文字没有丢失，保守分段本身不等于翻译失败，但验收应明确是否要求按阿拉伯语问号分句。

`find_residuals` 对整段原样保留的阿拉伯语或俄语返回空列表。实际 `check_translation_batch` 对阿拉伯语原文原样作为英语译文也没有返回问题。因此不能把确定性检查无 findings 当作“已翻译”的证明。这是源语残留启发式的覆盖边界，真实语义审校仍需单独测试；本轮没有验证模型审校是否能够发现它。

## 真实模型与人工验收待办

对六个方向分别使用同一组材料，记录翻译模型、独立审校模型、模型版本和任务 ID。目标为阿拉伯语时指定现代标准阿拉伯语，领域与术语库保持一致。按含义复核，不要求与草稿逐字相同，也不以回译相似度作为唯一标准。

| 样本 | 必须核查 |
| --- | --- |
| plain | 主体、动作、目的完整，无增译 |
| negation | “不意味着”“所有”及其作用范围不变 |
| question | 两个问题保留，问号和句序正确 |
| mixed_digits | 2026、1,234、95.5% 数值不变，AI 保留 |
| latin_prefix | 英文缩写不变，阿拉伯语段落方向正确，括号配对 |
| tokens | `{user_name}`、邮箱和 URL 内容逐字保留 |
| diacritics | 组合符号显示、光标移动、选择、复制及保存正常；译文是否使用变音符号按需求判断 |
| arabic_indic_digits | `١٢٣٤` 的数值和要求保留的字符不变 |

界面还需在 980px 和窄窗口验证长段落、编辑光标、Home/End、左右键、选中文本、复制粘贴、刷新恢复、分页导航及拆分／合并。导出还需覆盖多页长文、标题、列表、表格、图注与标注，并用 Microsoft Word 和实际 EPUB 阅读器打开。XLSX、TBX、TMX 资产导出、PDF 原文输入、阿拉伯语扫描件 OCR 和学术报告导出未在本轮覆盖。

## 重复运行

使用项目现有 Python 环境：

```bash
python3 scripts/arabic_acceptance_audit.py --out /tmp/folith-arabic-acceptance
```

脚本验证的是 Unicode、程序链路和导出结构，发现程序断言失败时非零退出；方向设置以 JSON 观测值记录，不将当前已知 RTL 缺口计为“通过”。`--skip-ui` 可仅执行核心与导出检查。浏览器和 LibreOffice 证据是本轮另外执行的视觉检查，脚本不会自动生成它们。
