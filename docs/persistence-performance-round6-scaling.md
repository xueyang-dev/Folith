# 长文档持久化性能（第六轮）：规模曲线推翻了"已降到可接受范围"

基线：第五轮之后的**工作树**（未改一行生产代码）。日期：2026-09-25。

> 与第三/四/五轮的关系：第三轮在 5000 段上量到 `state.json` 写放大 **84.0×**，
> 低于它自己设的 Phase B 门槛（100×），于是结论是
> **"Phase B NOT JUSTIFIED BY DATA"**；第四轮把 TM 也压到 79.3×，两轮合起来的结论是
> "持久化已降到合理区间"。**本轮把文档规模往上推一档，这个结论就不成立了。**
> 写放大不是常数，而是**随文档规模线性增长**——5000 段的 84.0× 只是这条直线上的一个点。

---

## Final verdict

**FAIL（针对"已降到可接受范围"这个结论）——O(n²) 没有被消除，只是被压低了常数。**

- **写放大是 O(n)，不是 O(1)。** 生产口径下 `st_x ≈ 0.0166 × 段数`：

  | 段数 | 5,000 | 10,000 | 20,000 |
  | --- | ---: | ---: | ---: |
  | `state.json` 写放大 | 84.0× | **166.5×** | **332.0×** |
  | TM 写放大 | 79.3× | **157.2×** | **313.7×** |

  每翻一倍段数，放大**翻一倍**。按 `st_x ≈ 0.0166n` 外推：
  **100× 的门槛在约 6,000 段就被越过**——第三轮是在 5,000 段（门槛下方 16% 处）测的。
- **累计写入是 O(n²)。** 20,000 段：`state.json` 累计写 **14,013.55MB**（14GB），
  TM 累计 **1,753.02MB**，单次运行合计约 **15.8GB**。
- **`json_serialization` 是 O(n²)**：5,000→10,000 段 **4.11×**，10,000→20,000 段 **4.21×**
  （每翻倍应为 4×）。20,000 段单次运行 **59.02s**。
- **Phase B 的四道门现在触发三道**（第三轮只触发零道）：

  | Gate | 阈值 | 5,000 段 | 10,000 段 | 20,000 段 |
  | --- | --- | ---: | ---: | ---: |
  | A `state_commit` > 整轮 25% | 25% | **42%** ✅ | **40%** ✅ | **35%** ✅ |
  | B `state_commit` > 100s | 100s | 4.92s ❌ | 18.48s ❌ | 76.83s ❌（逼近） |
  | C 写放大 > 100× | 100× | 84.0× ❌ | **166.5×** ✅ | **332.0×** ✅ |
  | D 全量快照是前二瓶颈 | — | **#1** ✅ | **#1** ✅ | **#1** ✅ |

- **第三轮的 "NOT JUSTIFIED" 是两个口径问题的叠加**：Gate A 用的是带 shim 的 8.0%
  （生产口径是 42%，第五轮已证明带 shim 的份额不可用），Gate C 恰好卡在 5,000 段
  这个门槛下方的测量点上。**两个问题都指向同一个教训：结论必须标"在哪个规模、
  哪个口径下成立"。**

**本轮同样不改代码。** 结论是"**该做 Phase B 了**"，而 Phase B 是独立一轮的架构改动
（journal + 强类型 mutation + 幂等重放 + compaction + 6 类崩溃测试）。

## 规模曲线（生产口径，去掉 shim）

`env -u PYTHONPATH venv/bin/python scripts/translation_persistence_audit.py \
    --sizes 1000,5000,10000,20000 --batch-size 4`

| 段数 | 批数 | 整轮 wall | 快照次数 | `state_commit` | 每次保存 | `st_MB` | **`st_x`** | `tm_s` | `tm_MB` | **`tm_x`** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 250 | 0.70s | 32 | 0.22s | 1.07ms | 37.24 | 17.8 | 0.03s | 4.69 | 16.9 |
| 5,000 | 1,250 | 11.73s | 157 | 4.92s | 4.38ms | 881.21 | 84.0 | 0.45s | 110.57 | 79.3 |
| 10,000 | 2,500 | 46.74s | 313 | 18.48s | 8.29ms | 3,497.99 | **166.5** | 2.01s | 438.39 | **157.2** |
| 20,000 | 5,000 | 217.16s | 626 | 76.83s | 17.92ms | 14,013.55 | **332.0** | 12.25s | 1,753.02 | **313.7** |

**为什么必然是 O(n²)**（这次是结构推导，不只是拟合）：

- 快照节奏被第三轮定死为 `min(8 批, ceil(总批数/10))`，并按"崩溃后最多重算 32 段"设了硬上限。
  于是**快照次数 = 批数 / 8 = 段数 / 32**，即 **O(n)**。
- 每次快照序列化的是**整份** `state.json`，字节数 **O(n)**。
- 累计写入 = O(n) × O(n) = **O(n²)**；写放大 = 累计 / 终态 = O(n²) / O(n) = **O(n)**。

**只要"每 32 段重写整份快照"这个形状不变，放大就一定是 O(n)。**
降常数（压缩、瘦身）能把直线压平一点，但**改变不了斜率**——斜率只能靠
"不再重写整份文档"来改，也就是 Phase B 的 journal。

拟合检验（`st_x / n`）：84.0/5000 = 0.01680，166.5/10000 = 0.01665，
332.0/20000 = 0.01660 —— 三个点在同一条直线上，偏差 <1.2%。

## 与"生产可用性"的关系（诚实标注）

必须把两件事分开：

1. **份额（share）依赖 fixture，不能作为结论。** 本轮整轮是 217s，用的是**零时延假 LLM**。
   真实 provider 下 20,000 段的任务是小时级，89s 只占个位数百分比。
   所以**"持久化占整轮 41%"这句话只在假 LLM 口径下成立**，本报告不把它当结论。
2. **绝对量与斜率与 fixture 无关，是真实成本。** 89s 的阻塞 CPU、15.8GB 的写入，
   在真实 provider 下一样要花。而**斜率**才是关键：再翻一倍规模就是 ~356s / ~63GB。

因此本轮的判据是**斜率 + 绝对量**，不是份额。这也是第三轮 Gate A 用份额做门槛
会得出错误结论的原因——**份额型门槛在假 LLM 口径下没有意义**。

## 为什么 Phase B 是唯一的结构性答案

要让累计写入不再是 O(n²)，只有两条路：

| 方案 | 能否改斜率 | 代价 |
| --- | --- | --- |
| 降常数（紧凑编码、载荷瘦身、更快序列化） | **不能** | 便宜，但只是把直线压低 |
| **拉长快照间隔** | 能（次数 O(n)→O(1)） | **崩溃后重算窗口爆炸**：把间隔从 32 段拉到 n/10 段，20,000 段时要重算 2,000 段 |
| **journal（Phase B）** | **能** | 架构改动；但**重放不重算**，所以快照可以很少而崩溃窗口不涨 |

关键点：**第三轮把"崩溃窗口 ≤32 段"当成硬约束，是因为当时没有 journal——
崩溃只能靠重算。** 一旦有了幂等的强类型 mutation journal，崩溃靠**重放**恢复，
快照间隔就可以拉长，而崩溃代价不再随间隔增长。这正是 Phase B 存在的理由。

**第三轮已经把这套设计写完了**（见 `docs/persistence-performance-phase3.md`
的「Phase B 设计（已设计未实施）」）：独立 `state_journal.jsonl`、
6 种强类型 mutation、重放幂等、compaction 顺序固定（绝不先清 journal）、
6 类崩溃语义测试。本轮**不需要重新设计，只需要按数据把门打开**。

## 下一轮最值得做的一项

**一个：按第三轮已写好的设计实施 Phase B（`state_journal.jsonl`）。**

门槛证据（本轮新增）：

| 依据 | 数值 |
| --- | --- |
| Gate A（份额） | 5,000 / 10,000 / 20,000 段分别是 42% / 40% / 35%，**全部 >25%** |
| Gate C（放大） | 10,000 段 **166.5×**、20,000 段 **332.0×**，**全部 >100×**；门槛在约 6,000 段越过 |
| Gate D（排名） | `save_job_state` 在三个规模上**都是第 1 名**，20,000 段占 35% |
| 斜率 | `json_serialization` 与 `review_truth_reconcile` 均实测 **O(n²)**（每翻倍 4.0–4.2×） |

**实施顺序（建议）**：

1. **只做翻译热路径**的 `translation_batch_committed` 一种 mutation，先跑通
   "写 journal → 崩溃 → 重放 → 不重算"这一条闭环，并用 6 类崩溃测试钉住。
2. 快照间隔从 8 批放大到"按 journal 字节数"触发（例如 journal 超过 32MB 时压一次），
   让快照次数**与段数解耦**。
3. 再补其余 5 种 mutation（`review_batch_committed`、`translation_truth_changed`、
   `finding_batch_appended`、`tm_promotion_recorded`、`stage_transition`）。
4. compaction 顺序严格按第三轮 §13：建新快照 → temp → 原子替换 → 标记已应用 → **确认安全后才删**。

**为什么不是别的**：

- **`review_truth`/`dependency_truth` 文本换摘要（第五轮的建议）**：本轮**主动降级**。
  它能把主导项砍 41%（20,000 段 `json_serialization` 59.0s → ~34.8s），
  但**斜率不变**，而且它改的是 `state.json` 的持久化表示——
  **在快照策略即将被 Phase B 重做之前改持久化表示，兼容工作要白做一次。**
  正确顺序是 Phase B 先行，载荷瘦身作为它的后续优化（快照变小，收益还能放大）。
- **`review_truth_reconcile` 的 O(n²) 扫描（20,000 段 11.47s）**：同样受制于
  "没有变更信号"。journal 天然提供这个信号（重放时按 mutation 应用），
  所以**它应该作为 Phase B 的一部分解决，而不是单独打补丁**。
